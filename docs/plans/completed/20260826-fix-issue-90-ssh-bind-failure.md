# Issue #90: демон регистрируется online, когда его SSH-сервер не смог занять порт

## Overview

Issue #90 сообщает: `startSSH` (`internal/agent/daemon.go:658-675`) запускает SSH-сервер в горутине и
безусловно возвращает `nil`. Ошибка `net.Listen` из `SSHServer.Start`
(`internal/agent/sshserver.go:129-132`) до вызывающего не доходит никогда. `Run` идёт дальше в
`registerAndSubscribe`, демон регистрируется, и хаб раздаёт каждому пиру `d.sshPort` — порт, которым
этот процесс не владеет. Устройство показано **online**, пиры монтируются с него, и ни в хабе, ни в
`hubfuse devices`, ни в логах пира нет ничего, что сказало бы «эту шару обслужить невозможно».

### Воспроизведено на master

Сценарный тест (сквоттер занимает порт, затем стартует демон) на текущем master, Linux:

```
zz_repro90_test.go:29: DAEMON LOG:
    10:47:34 [INFO]  connecting to hub addr=127.0.0.1:45597
    10:47:34 [INFO]  connected to hub
    10:47:34 [ERROR] SSH server stopped error=listen on port 41467: listen tcp :41467: bind: address already in use
    10:47:34 [INFO]  registered with hub online_devices=1
zz_repro90_test.go:36: RESULT: alice sees bob present=true status="online" ip="127.0.0.1"
--- PASS: TestRepro90Baseline (0.71s)
```

Ровно то, что описано в issue: bind провалился, «registered with hub» строкой ниже, сосед видит
устройство как `online`. 0.71 с.

Попутно измерено то, о чём issue говорит отдельно: **`helpers.launchDaemon` не заметил ничего.**
`WaitForPort` дозвонился до **сквоттера** и решил, что агент поднялся. Значит слепое пятно хелпера —
не гипотеза, а факт того же прогона.

### Измерение, которое решает выбор дизайна

Главный аргумент против «просто падать громко» — что bind может провалиться *транзиторно* (рестарт
гонится с сокетом предыдущего процесса), и тогда громкое падение убьёт демон, который сам бы
поднялся. **Это измерено и оказалось неверным для этого репозитория.**

`hubfuse restart` не гонится ни с чем: `SignalStop` (`internal/common/daemonize/control.go:23`) шлёт
SIGTERM, ждёт выхода (`waitForExit`), эскалирует до SIGKILL и возвращает управление только после
подтверждённого выхода; `restartCmd` запускает замену строго после этого. Остаётся вопрос, свободен
ли порт сразу после выхода. Пробник (`net.Listen` из отдельного процесса; у уходящего процесса есть
установленное соединение, то есть после выхода в ядре остаётся сокет в TIME_WAIT), Linux 6.8,
go1.26.7, 5 прогонов:

| момент | результат |
|---|---|
| пока прежний процесс держит порт | `bind: address already in use` — 5/5 |
| сразу после подтверждённого выхода, попытка №0 | **успех — 5/5**, t = 29–64 мкс |

Ни одного повтора не понадобилось: `net.Listen` в Go ставит `SO_REUSEADDR`, TIME_WAIT слушающему
сокету не мешает. **Транзиторного EADDRINUSE в путях этого репозитория нет** — измерено на Linux; на
darwin не измерялось, и текст этого не утверждает.

Оставшиеся причины отказа bind тоже не транзиторны: чужой процесс на порту (реальный случай из
issue — забытый демон на 2222 при отладке #74) держится до вмешательства человека, а `EACCES` на
порту < 1024 не проходит никогда. Ретрай в такой ситуации только оттягивает диагноз.

### Второй дефект того же вида: смерть accept-петли

Issue отдельно просит учесть, что bind может «отказать после успешного старта». Здесь нашёлся
конкретный второй экземпляр того же бага. Accept-петля `SSHServer.Start` возвращает ошибку при любом
отказе `ln.Accept()`, а `startSSH` эту ошибку только логирует. Что именно доходит до `Accept`,
проверено по первоисточнику — `internal/poll.(*FD).Accept` в используемом тулчейне (go1.26.7,
`/snap/go/11262/src/internal/poll/fd_unix.go`):

```go
switch err {
case syscall.EINTR:        continue
case syscall.EAGAIN:       ... continue
case syscall.ECONNABORTED: continue   // "it's a silly error, so try again"
}
return -1, nil, errcall, err
```

`EINTR`/`EAGAIN`/`ECONNABORTED` поллер гасит сам. Всё остальное — в том числе `EMFILE`/`ENFILE`
(исчерпание дескрипторов) — доходит до `net.Listener.Accept`. То есть один момент нехватки fd сегодня
**навсегда** убивает SSH-сервер, оставляя демон зарегистрированным и online. Это ровно баг #90, но
через другую дверь, поэтому лечится здесь же, а не заводится отдельно.

## Solution Overview

**Решение: живость SSH-слушателя становится предусловием того, что демон вообще что-то объявляет
хабу.** Два механизма, оба вытекают из одного правила.

1. **Старт: bind синхронный, отказ — громкий, без ретраев.** `SSHServer.Start` расщепляется на
   `Listen()` (bind, возвращает ошибку) и `Serve(ctx)` (accept-петля); `Start` остаётся композицией
   этих двух, поэтому два существующих теста в `sshserver_test.go` не трогаются вовсе. `startSSH`
   зовёт `Listen()` синхронно — ошибка идёт через `Run` наверх, `hubfuse start` выходит ненулевым
   кодом, PID-файл не пишется (`onReady` живёт в `sessionOnce`, который в этом сценарии не
   выполняется), хабу не сказано ничего. Это прецедент #69: «демону нечего делать — падай и скажи».

2. **Жизнь: смерть accept-петли снимает устройство с хаба.** После успешного bind петля
   классифицирует свой выход:
   - контекст отменён или `Stop()` закрыл слушателя намеренно → `nil`, как сегодня;
   - `EMFILE`/`ENFILE`/`ENOBUFS`/`ENOMEM` → **ретрай с backoff 5 мс → 1 с**, а не смерть: сокет
     по-прежнему НАШ, соединения копятся в backlog, и «на секунду кончились дескрипторы» — это не
     «обслуживать нечего». Сегодня это убивает сервер навсегда и молча;
   - что угодно ещё → фатально: ошибка уходит в буферизованный канал `sshDied`, `runServices`
     читает его наравне с `ctx.Done()`, отменяет производный контекст демона и зовёт `Shutdown()`.
     `Shutdown` делает `Deregister`, хаб рассылает offline, пиры размонтируют. `Run` возвращает
     ошибку — код выхода ненулевой, причина в логе.

Пункт 2 — это и есть ответ на «зарегистрироваться в состоянии, которое говорит пирам, что шары
недоступны», только достигнутый существующим механизмом (`Deregister` → offline → размонтирование),
без единой правки proto и без нового состояния в хабе.

Отмена производного контекста перед `Shutdown` обязательна и не косметика: `supervise` в этот момент
жив и на своём backoff переустанавливает сессию. Без отмены его `Register` мог бы лечь **после**
нашего `Deregister` и вернуть устройство в online — ровно тот призрак, который чинится. `Run`
оборачивает входной ctx в `context.WithCancel` (`defer cancel()`), и ветка `sshDied` зовёт `cancel()`
до `Shutdown()`.

### Отвергнутые варианты

- **Ретрай bind, падать только если не поднялось (вариант «C» из issue).** Отвергнут измерением
  выше: транзиторного EADDRINUSE в путях этого репозитория нет (`restart` ждёт подтверждённого
  выхода; повторный bind после выхода успешен с первой попытки, 5/5, 29–64 мкс). Все реальные
  причины отказа держатся до действий человека, и ретрай лишь оттягивает диагноз — то самое, из-за
  чего дефект и жил незамеченным.

- **Регистрироваться с пустым списком шар («вариант B»).** Технически возможен и проверен:
  `handleSharesUpdated` действительно размонтирует у пира исчезнувшие шары, изменений proto не
  нужно. Отвергнут по трём причинам. Во-первых, он паркует демон в состоянии «online, но не
  обслуживает ничего», которого не объясняет ни одна CLI-поверхность: `hubfuse devices` покажет
  устройство online, и оператору останется гадать. Во-вторых, он вводит инвариант «удерживать и
  переопубликовывать шары» сразу в три места публикации (Register на переподключении,
  `UpdateShares` при hot-reload конфига, восстановление после возврата слушателя) — три места, где
  его можно забыть, против одного правила «нет слушателя — нет демона». В-третьих, наблюдаемый у
  пира результат тот же самый, что даёт `Deregister` из пункта 2, но дороже.

- **Оставить всё как есть и только залогировать громче.** Отвергнут: сегодня строка `[ERROR] SSH
  server stopped` УЖЕ пишется (см. вывод воспроизведения) и ничего не меняет — следующей строкой
  идёт `registered with hub`. Дефект не в громкости лога, а в том, что процесс продолжает
  объявлять то, чего у него нет.

- **Считать фатальной любую ошибку accept, без класса транзиторных.** Отвергнут: это превратило бы
  секундную нехватку дескрипторов в смерть демона, при том что сокет остаётся нашим и backlog
  никуда не делся. Прецедент — `net/http.Server.Serve`, который ровно эти ошибки переживает с
  backoff до 1 с.

### Про `WaitForPort` — в scope

Слепое пятно `helpers.WaitForPort` (принимает любого слушателя на порту, включая сквоттера) — **в
scope**, потому что после фикса оно активно вредит: демон со сквоттером теперь выходит, а
`launchDaemon` всё равно дозвонится до сквоттера и вернёт управление, и тест упадёт позже и не по
делу. Лечится тем, что `launchDaemon` дополнительно ждёт собственную строку демона `ssh server
listening`: сквоттер умеет ответить на TCP-дозвон, но не умеет написать это в лог демона. Сам
`WaitForPort` не трогается — он используется и для хаба, где ложного слушателя взяться неоткуда.

### Принятое следствие

Демон, который ничего не экспортирует и только монтирует чужое, сегодня переживает занятый порт, а
после фикса — выходит. Это принято сознательно: `Register` в любом случае раздаёт `d.sshPort` всем
пирам, а спаривание предполагает работающий SSH-сервер, так что «клиент-только» — не отдельный
поддерживаемый режим, а конфигурация, у которой просто пусто в `shares`. Правило «нет слушателя —
нет демона» одно на всех, и это дешевле, чем второе правило для полуслучая.

## Technical Details

`internal/agent/sshserver.go`:

```go
func (s *SSHServer) Listen() error            // bind, сохраняет s.listener
func (s *SSHServer) Serve(ctx context.Context) error  // accept-петля
func (s *SSHServer) Start(ctx context.Context) error  // Listen + Serve (совместимость)
```

`Stop()` дополнительно выставляет `s.stopping` под тем же мьютексом до `ln.Close()`, чтобы `Serve`
отличал «нас закрыли намеренно» от «слушатель умер» явно, а не по совпадению порядка
«ctx отменён → Shutdown → Stop».

`isTransientAcceptError(err) bool` — `errors.Is` по `syscall.EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`
(не `net.Error.Temporary()`: deprecated, staticcheck SA1019).

`internal/agent/daemon.go`:

- поле `sshDied chan error` (буфер 1) — почему буфер: `Serve` может умереть между `startSSH` и
  `runServices`, и небуферизованная отправка либо потеряла бы ошибку, либо заблокировала горутину
  навсегда. Отправка неблокирующая (`select`/`default`), приём — в `select` `runServices`. Нулевое
  значение (nil-канал) безопасно в обе стороны: неблокирующая отправка уходит в `default`, приём в
  `select` просто никогда не срабатывает — это важно, потому что `buildTestDaemon` собирает `Daemon`
  структурным литералом;
- `startSSH`: `Listen()` синхронно, затем `go Serve(ctx)`;
- `Run`: оборачивает ctx в `context.WithCancel` с `defer cancel()`;
- `runServices`: `select` на `ctx.Done()` и `d.sshDied`.
