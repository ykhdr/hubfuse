# Issue #74: macOS отбирает у демона доступ в локальную сеть, и отказ нечитаем

## Overview

Issue #74 сообщает: на macOS демон агента через короткое время лишается доступа в LAN, соединение с
хабом рвётся, любой следующий дозвон отдаёт `connect: no route to host`, и демон навсегда бесполезен
— при том что сертификаты валидны, хаб пингуется, а одноразовые CLI-команды работают. Предлагается
три фикса: LaunchAgent (чтобы GUI-промпт вообще мог появиться), детект сигнатуры отказа с внятным
сообщением, и документация.

**Отказ воспроизведён на ТЕКУЩЕМ master, на живом стенде, целиком.** Свежесобранный бинарь master
(darwin/arm64, подписан ad-hoc) на маке `192.168.31.63` против хаба `192.168.31.158:9090`:

```
23:35:58 registered with hub online_devices=2            ← работает
23:36:53 heartbeat failed … keepalive ping failed to receive ACK within timeout
23:36:53 event stream error … keepalive ping failed to receive ACK within timeout
23:36:53 hub session lost; reconnecting
23:36:53 … connect: no route to host   backoff=1s
…        … connect: no route to host   backoff=1m0s     ← и так навсегда
```

Регистрация на t=0, обрыв примерно на **t+40 с** (keepalive из #72 замечает его на t+55 с, то есть
через свои ~15 с — механизм работает ровно как задумано), дальше `no route to host` бесконечно. Хаб
при этом видит устройство как `online`, потом `offline`.

### Что измерено про механизм

Ключ — **идентичность бинаря**, а не «долгоживущий против одноразового». Четыре прогона на том же
маке, в тот же хаб, в течение получаса:

| что запускали | результат |
|---|---|
| `~/go/bin/hubfuse` (установлен 16 авг), `start` | **отказ на t=0**, мгновенно, `no route to host`, демон выходит |
| `~/go/bin/hubfuse devices` (тот же бинарь, одноразовая команда) | **работает**, список устройств получен |
| те же байты, скопированы и переподписаны `codesign -f -s -`, `start` | **регистрируется и живёт** |
| свежесобранный master, подписан сегодня, `start` | регистрируется, **обрыв через ~40 с** |
| посторонний Go-пробник (только исходящие соединения, БЕЗ слушающего сокета), 150 с | **30/30 дозвонов успешны**, обрыва нет |

Отсюда картина, которой в issue нет:

1. **Решение привязано к идентичности бинаря.** Те же байты по другому пути и с новой подписью
   ведут себя противоположно установленному пути. Для `~/go/bin/hubfuse` решение «запретить» уже
   записано (с августа), поэтому у него нет никакого окна — отказ мгновенный. Для новой
   идентичности окно есть.
2. **Окно ~40 секунд реально** — но это окно НОВОЙ идентичности, а не свойство всех запусков. Именно
   поэтому одноразовая `hubfuse devices` успевает отработать, а `hubfuse start` нет: дело не в том,
   что процесс долгоживущий, а в том, что он переживает окно.
3. **Триггером выступает СЛУШАЮЩИЙ сокет, а не исходящий трафик.** Пробник, который 150 секунд
   ходил на тот же адрес и никого не слушал, не пострадал вовсе. `hubfuse start` поднимает
   встроенный SSH-сервер (`ssh server listening port=2222`) — вот что вводит процесс в область
   действия проверки.

### Что в issue неверно

**Контрольный опыт с копией `nc`, на котором держится вывод issue («identical bytes, identical
destination, different path → значит блокируют идентичность процесса, а не сеть»), измеряет не то.**
Проверено сегодня:

| бинарь | цель | результат |
|---|---|---|
| `/usr/bin/nc` | LAN-хаб | rc=0, соединение установлено |
| `/tmp/nc2` (копия) | LAN-хаб | **rc=137 (SIGKILL)** |
| `/tmp/nc2` (копия) | **127.0.0.1** | rc=137 |
| `/tmp/nc2` (копия) | **1.1.1.1**, публичный адрес | rc=137 |

Копия убивается независимо от адресата — включая loopback и публичный интернет. Это принуждение
подписи кода к бинарю, вынесенному из подписанного системного тома, а не сеть; `spctl -a -vv` на
копии говорит `invalid signature (code or signature have been modified)`. Тот же SIGKILL получал и
собственный Go-пробник, пока его не переподписали `codesign -f -s -`.

Вывод issue при этом **оказался верным** — просто доказан он был не тем опытом. Настоящее
доказательство привязки к идентичности — третья строка таблицы выше: те же байты, новая подпись,
противоположное поведение.

### Второй, независимый дефект: отказ действительно нечитаем

Issue права и в этом, и здесь нашёлся конкретный баг **в текущем master**, воспроизводимый на Linux
без всякого мака:

```
error: device "transport: Error while dialing: dial tcp 192.168.31.158:9090: connect: no route to host" is offline
```

`cmd/internal/clierrors/clierrors.go:208-210` на КАЖДЫЙ `codes.Unavailable` зовёт
`extractNickname(msg)`, а тот первым делом берёт первую подстроку в двойных кавычках
(`quotedDoubleRe`, `:269-271`). gRPC оборачивает ошибку дозвона в кавычки
(`connection error: desc = "transport: …"`), поэтому текст транспортной ошибки становится
«никнеймом устройства». Ветка «не могу достучаться до хаба» (`:216-221`), которая знает про
`ctx.HubAddr`, стоит НИЖЕ и не получает управления никогда — проверено: даже с заполненным
`HubAddr` сообщение остаётся тем же.

То есть оператор, у которого недоступен хаб, получает сообщение про несуществующее устройство с
транспортной ошибкой вместо имени. Это ровно то «generic dial error sends the operator looking at
routing», о котором пишет issue, только хуже — оно уводит ещё и в сторону чужого устройства.

## Context (from discovery)

**Стенд.** Linux `192.168.31.158` (хаб `hubfuse-hub` v0.1.2 + агент `server`), мак
`khudorozhkov-2.local` = `192.168.31.63`, macOS 26.4 arm64, доступ по SSH как `mac`. Устройство
`mac` было выпрото с хаба ретеншеном, поэтому для прогонов оно перезаведено заново
(`hubfuse join --force`); прежний `~/.hubfuse` сохранён в `~/.hubfuse.bak-1787675438`. На маке стоит
Go 1.21.13 — **собрать этот проект (Go 1.25) там уже нельзя**, поэтому бинарь кросс-собирается на
Linux (`GOOS=darwin GOARCH=arm64`), копируется и подписывается на месте `codesign -f -s -`; без
подписи macOS 26 убивает процесс на exec (SIGKILL, без вывода). Это же относится к любому
готовому бинарю из релиза, если он не подписан — важно для инструкции в README.

**Код репозитория:**

- `cmd/internal/clierrors/clierrors.go:208-221` — разбор `codes.Unavailable`, где `extractNickname`
  побеждает ветку `HubAddr`; `:268-284` — сам `extractNickname` и его `quotedDoubleRe`.
- `internal/agent/connector.go` — `Dial`/`Connect`; ошибки дозвона отдаются как есть.
- `internal/agent/daemon.go` — `reconnectSession` логирует `hub session reconnect failed, retrying`
  с backoff'ом до `backoffMax` (60 с) и повторяет это бесконечно; ничего не говорит о том, что
  причина отказа не в сети.
- `internal/agent/client.go` — `isKeepalivePunished` (#78): готовый образец «классификатор по тексту
  ошибки + ОДИН Error за жизнь процесса», на который здесь нужно опереться, а не изобретать заново.
- `internal/agent/sshserver.go` — встроенный SSH-сервер, порт 2222. Это и есть слушающий сокет,
  который вводит демона в область действия проверки macOS.
- Ни LaunchAgent-plist, ни команды установки в репозитории нет; `.goreleaser.yaml` собирает
  darwin-архивы, но ничего про подпись и про local network не говорит.

- **unit** (`internal/agent`): классификатор local-network отказа — срабатывает на дословной
  ошибке с мака, молчит на обычном `Unavailable`, на отменённом контексте и на отказе к ПУБЛИЧНОМУ
  адресу; логируется ровно один раз за жизнь процесса
- **unit** (`cmd/hubfuse`): генерация plist — содержимое, путь, идемпотентность, отказ на не-darwin
- приёмка на маке (не автотест, руками, записывается в план): установить LaunchAgent, одобрить
  промпт, убедиться что демон живёт дольше окна и переживает перезагрузку

## Solution Overview

Три части, в порядке ценности за единицу риска.

1. **Перестать врать в сообщении об ошибке** (`clierrors`). Недостижимый хаб обязан читаться как
   недостижимый хаб. Это чистый баг, чинится и тестируется на Linux, и он бьёт по ВСЕМ платформам,
   не только по macOS.

2. **Назвать причину, когда она диагностируема** (агент). По образцу `isKeepalivePunished` (#78):
   классификатор «повторный отказ дозвона с `no route to host` (EHOSTUNREACH) к ЧАСТНОМУ адресу на
   darwin», и ОДИН Error за жизнь процесса с конкретным действием — System Settings → Privacy &
   Security → Local Network, и указание, что демон, запущенный по SSH, промпт показать не может.
   Условие на частный адрес обязательно: `no route to host` к публичному адресу — это обычная
   сетевая авария, и называть её проблемой прав было бы новой неправдой.

3. **Дать поддерживаемый способ получить разрешение** — LaunchAgent под пользовательской
   GUI-сессией плюс команда установки. Только так промпт вообще может появиться.

Чего план НЕ делает: не пытается обойти macOS программно (обхода нет), не трогает хаб, не меняет
keepalive и не объявляет macOS-поведение багом HubFuse — оно им не является. Задача — чтобы отказ
был назван и чтобы существовал документированный путь его не иметь.
