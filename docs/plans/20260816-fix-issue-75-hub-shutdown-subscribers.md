# Issue #75: хаб не завершается по SIGTERM, пока к нему подключён хоть один агент

## Overview

`Hub.Stop` вызывает `grpcServer.GracefulStop()`, который по контракту ждёт завершения КАЖДОГО
in-flight RPC. `Subscribe` — долгоживущий server-stream: его хендлер выходит только когда уходит
клиент. `hubfuse-hub stop` шлёт SIGTERM, ждёт 10 секунд (`daemonize.stopGracefulTimeout`) и
добивает процесс SIGKILL.

Issue сформулирован как «хаб виснет, пока открыт ЗАЛИПШИЙ (#72) стрим». **Измерения показывают,
что залипшее соединение не является необходимым условием** — достаточно одного здорового агента:

| Конфигурация | Время от SIGTERM до выхода процесса |
|---|---|
| хаб без подписчиков | **10.5 мс** |
| хаб + один живой ЗДОРОВЫЙ демон | **29.99 с** (затем SIGKILL) |
| хаб + демон, остановленный заранее (`Deregister`) | **11 мс** |
| `helpers.Hub.Restart` с живым агентом | 5.06 с, старый процесс добит SIGKILL |

29.987767369 с — это с точностью до 13 мс `maxHeartbeatFailures` (3, `agent/daemon.go:613`) ×
`defaultHeartbeatInterval` (10s, `agent/heartbeat.go:12`). То есть хаб держит не мёртвое
соединение, а **протокол выхода живого агента**: хаб ждёт, пока агент сам решит, что сессия
мертва. Строка «11 мс» — это тот же путь, но после `Deregister` → `removeSubscriber` → `close(ch)`,
и она же является эмпирическим доказательством фикса: закрытие каналов подписчиков превращает
29.99 с в 11 мс.

Причина, по которой GOAWAY не помогает: первый GOAWAY не закрывает существующие стримы
(`http2_client.go:1346-1355`, комментарий там явный), поэтому `Subscribe` здорового агента держит
соединение в `s.conns`, а `GracefulStop` ждёт именно `len(s.conns) == 0` (`server.go:1972`).

Предложенный в issue пункт 3 (серверный keepalive) **уже сделан** в #72
(`internal/hub/serveropts.go`) и в скоуп не входит. Опереться на него как на верхнюю границу
нельзя: keepalive-пинг не отправляется вовсе, пока с соединения приходят кадры
(`http2_server.go:1231-1239`: `if lastRead > prevNano { ...; continue }`), а агент шлёт heartbeat
каждые 10 секунд по тому же транспорту.

## Context (from discovery)

**Проверено по исходникам grpc-go v1.79.3:**

- `server.go:885-892` — defer в `Serve`: `s.serveWG.Done(); if s.quit.HasFired() { <-s.done.Done() }`.
  `done` срабатывает только после `serveWG.Wait()`, `for len(s.conns) != 0 { s.cv.Wait() }` (:1972)
  и, на graceful-пути, `handlersWG.Wait()` (:1985-1986). **Следствие, определяющее весь дизайн:**
  ранний возврат из `Hub.Stop` освобождает горутину, которую никто не ждёт, а главная горутина
  продолжает стоять в `Serve` до полного завершения `stop()`. Ограничение shutdown по времени
  **обязано заканчиваться явным `os.Exit`**, иначе это фикция.
- `server.go:1952-1953` — `stop()`: `s.quit.Fire(); defer s.done.Fire()`. Конкурентный вызов
  `Stop()` во время висящего `GracefulStop()` легален (`s.cv = sync.NewCond(&s.mu)`, :710), но оба
  блокируются на ожидании соединений, поэтому **оба вызова делаются из горутин**.
- `server.go:1985` — `if graceful || s.opts.waitForHandlers { s.handlersWG.Wait() }`: после
  форсированного `Stop()` хендлеры остаются ЖИВЫМИ. Ловушка: `grpc.WaitForHandlers(true)` выглядит
  решением, но даёт неограниченное ожидание — **не добавлять**.
- `http2_server.go:1414-1421` — между первым и вторым GOAWAY стоит захардкоженный
  `time.NewTimer(5 * time.Second)`; второй GOAWAY и есть то, что реально роняет соединение.
  Именно против этих **5 секунд** калибруется grace, а не против 10 секунд `SignalStop`.
- `http2Server.Close`: `close(t.done)` → `t.conn.Close()` (до 5 секунд на closeNotify при
  простаивающем writer'е, `crypto/tls/conn.go:1477`) → и только затем `s.cancel()` по каждому
  стриму. `w.done` — это `s.ctxDone` (`http2_server.go:610`), поэтому хендлер, застрявший в
  `wq.get` (`flowcontrol.go:54-66`), освобождается только ПОСЛЕ этих 5 секунд, и всё это под
  `s.mu` (`server.go:1963-1964, 1996-2002`).
- `http2_client.go:1383-1386` — при нулевом числе активных стримов клиент на первом же GOAWAY сам
  рвёт транспорт. Это и объясняет 11 мс: соединение снимает КЛИЕНТ, как только хендлер вернулся.

**Код хаба:**

- `internal/hub/hub.go:185-187` — `Stop()`: `Drain()` → свип → безусловный `GracefulStop()`.
  `sync.Once` нет: повторный вызов закроет store дважды.
- `internal/hub/hub.go:163-183` — свип: `ListOnlineDevices` + N × `UpdateDeviceStatus` на
  `context.Background()` без дедлайна. Store открыт с `SetMaxOpenConns(1)` (`store/sqlite.go:82`)
  и `PRAGMA busy_timeout = 5000` (:96): ОДИН `UpdateDeviceStatus` может ждать до 5 секунд, если
  параллельно пишет `hubfuse-hub issue-join`. Свип обязан перестать зависеть от N round-trip'ов.
- `internal/hub/hub.go:167-182` — **порядок внутри свипа опасен**: сначала `BroadcastAll`, потом
  `UpdateDeviceStatus`. Под ограниченным контекстом обрыв даёт худший из возможных исходов —
  событие доставлено, строка осталась `online`, то есть ровно тот фантом, ради которого в #69
  вводился `Drain`. Долговечная запись обязана идти ПЕРВОЙ.
- **Статусы устройств никто не сбрасывает при СТАРТЕ хаба**: есть только `MarkOnlineIfOffline`
  (`store/sqlite.go:246`) и путь `Register`, а первый `checkStale` heartbeat-монитора отстоит на
  целый `timeout/3` ≈ 10 секунд. Именно поэтому ограниченный по времени свип сегодня был бы
  неполноценным: у усечённого свипа нет страховки. Реконсиляция при старте — то, что делает
  ограниченный свип и форсированный `Stop()` безопасными (при SIGKILL/OOM/потере питания свип не
  отрабатывает вовсе, а хаб доверяет статусам из БД между рестартами).
- `internal/hub/registry.go:531-572` — `Broadcast`/`BroadcastAll` шлют в каналы подписчиков под
  **RLock**. Отсюда жёсткое требование: `CloseAllSubscribers` обязан брать **write-lock**, иначе
  конкурентный broadcast даёт `send on closed channel` и роняет хаб — причём именно в момент
  выключения, когда в полёте финальный `BroadcastAll`.
- `internal/hub/registry.go:60-90` — у `Join` нет drain-гарда вовсе, а первое, что он делает, —
  `consumeJoinToken`: умирающий хаб сжигает одноразовый токен и выдаёт сертификат, чей
  последующий `Register` будет отвергнут.
- `internal/hub/server.go:194-224` и `internal/hub/registry.go:496-516` — у `Subscribe` **нет
  никакого drain-гарда**: ни на уровне RPC, ни на уровне Registry.
- `internal/hub/registry.go:212-217` — `Heartbeat` не проверяет draining на входе и пишет
  `UpdateHeartbeat` до всех проверок: запись приходит после того, как свип посчитал устройства.
  Фантома не возникает (`canRecover` откажет, :299), но запись попадает в тот же интервал, где
  иначе мог бы отработать `store.Close()`.
- `internal/hub/heartbeat.go:106-131` — `checkStale` отдаёт ctx прямо в store и логирует на уровне
  **Error** (:110, :123). После отмены контекста при остановке это даёт Error-строки на КАЖДОМ
  штатном выключении.
- `internal/hub/hubtest/hubtest.go:172-179` — харнесс зовёт `grpcServer.GracefulStop()` напрямую,
  минуя `Hub.Stop`: фикс, написанный только в `hub.go`, до тестов не доедет.
- `cmd/hubfuse-hub/main.go:137-155` — сигнальную горутину с `h.Stop()` **никто не ждёт**, а
  `defer` с удалением pid-файла не выполнится при `os.Exit`.
- `h.grpcServer` пишется в `Start` (:111), читается в `Stop` (:185) без синхронизации; фоновые
  горутины (`:125`, `:127`) стартуют в `Start`, поэтому голая `WaitGroup` **не** закрывает дыру
  «Stop до Start»: `wg.Wait()` на пустой группе вернётся мгновенно, `store.Close()` отработает, и
  только потом `Start` поднимет монитор и `Serve` поверх закрытого store. Нужно явное состояние.
- `tests/scenarios/helpers/hub.go:132-140` — `Stop` ждёт 5 секунд и добивает `Kill`;
  `reconnect_test.go:36` (`hub.Restart`) платит эти 5 секунд + SIGKILL на каждом прогоне.
- `internal/common/daemonize/control.go:74-86` — `waitForExit` корректен только потому, что
  `hubfuse-hub stop` не является родителем хаба: `kill(pid,0)` на зомби возвращает nil, и вызов
  `SignalStop` из родительского процесса ждал бы полные 10+3 секунды и соврал бы «отказался
  выходить после SIGKILL». Требует комментария, чтобы это не сломали позже.
- `tests/testrelay/relay.go:92-105` — `Break()` продолжает ЧИТАТЬ и выбрасывать байты, поэтому
  сокет хаба не переполняется: реле воспроизводит залипание «хендлер в `select`» и принципиально
  не воспроизводит «хендлер в `Send`».

## Итоги брейншторма и дебатов

Рассматривались три принципиально разных подхода; на каждый заводился отдельный агент-критик с
ролью «жёсткий оппонент». Проведено три полных раунда: идея → атака → ответ и контратака →
ответ критика. Ниже — суть.

### Идея A — «закрыть все подписки»

`Registry.CloseAllSubscribers()` в `Hub.Stop`: каждый хендлер `Subscribe` получает `!ok` из
закрытого канала и возвращается. Без таймера, `GracefulStop` остаётся безусловным.

**Атака (принята):** (1) хендлер, застрявший в `stream.Send` на исчерпанном окне flow control,
закрытием канала не разблокируется — `writeQuota.get` ждёт только WINDOW_UPDATE или закрытия
транспорта; (2) предпосылка «серверный keepalive добьёт транспорт за ~20 с» ложна — пинг не
шлётся, пока клиент шлёт кадры; (3) `GracefulStop` ждёт закрытия СОЕДИНЕНИЙ, а не хендлеров, и
платит захардкоженные 5 секунд между двумя GOAWAY.

**Ответ:** все три пункта приняты (перепроверены по первоисточнику). Идея A в одиночку отвергнута.

**Контратака:** 5 секунд из п.3 платятся только когда клиент не ack-ает ping, то есть в залипшем
случае, где мы всё равно форсируем раньше; для здорового клиента это миллисекунды.

**Ответ критика (раунд 3):** контратака принята частично, вывод опровергнут: `tls.Conn.Close`
берёт быстрый путь, когда запись В ПРОЦЕССЕ, а 5 секунд `closeNotify` платятся в ОБРАТНОЙ
конфигурации (простаивающий writer, полный буфер отправки). Хуже того, в `http2Server.Close`
порядок такой: `close(t.done)` → `t.conn.Close()` (до 5 с) → и только затем `s.cancel()` по
стримам. Отсюда интерливинг длиннее 10 секунд: свип 0-5 с (один `UpdateDeviceStatus` может выждать
весь `busy_timeout`) + grace 3 с + форс, заблокированный 5 с на первом соединении = 13 с > 10 с →
SIGKILL. **Вывод, вошедший в решение:** и `GracefulStop()`, и форсированный `Stop()` вызываются
ИЗ ГОРУТИН, свип перестаёт быть N round-trip'ами, а выход по исчерпанию бюджета — это `os.Exit`.

### Идея B — «ограниченный по времени GracefulStop»

`GracefulStop` в горутине, по истечении grace — `grpcServer.Stop()`. Registry не трогаем.

**Атака (принята):** (1) без закрытия подписок graceful-ветка недостижима, таймер срабатывает
ВСЕГДА — shutdown превращается в безусловный `sleep grace` + разрыв; (2) порядок внутри `Hub.Stop`
ничего не гарантирует, пока `cmd` не ждёт `h.Stop()`; (3) форс рвёт in-flight `Join`, уже
потративший одноразовый токен; (4) свип без дедлайна вешает shutdown ещё до старта таймера.

**Ответ:** 1, 2, 4 приняты. По 3: цена реальна, но сегодня тот же `Join` обрывается SIGKILL'ом.

**Контратака:** после `CloseAllSubscribers` graceful-ветка становится основной, а таймер —
настоящим фолбэком.

**Ответ критика (раунд 3) — самый ценный вклад дебатов, критик ИЗМЕРИЛ:** 29.99 с с одним
здоровым агентом против 11 мс без подписчиков (таблица в Overview). Отсюда: закрытие каналов —
основной фикс, доказанный, а не выведенный; и **issue шире своего заголовка**. Плюс три уточнения,
вошедшие в решение: (a) соединение рвёт клиент на первом GOAWAY, поэтому здоровый случай стоит
миллисекунды; (b) но у grpc есть собственный 5-секундный таймер в drain-пути — grace калибруется
против него; (c) полуоткрытое соединение переживает `CloseAllSubscribers` и уходит только по
серверному keepalive (15+5 с), поэтому фолбэк — это «путь для мёртвого пира», а не «редкий путь».
Ещё одно следствие, которое критик потребовал зафиксировать: закрытие подписок ПОРОЖДАЕТ
реконнект-шторм (`backoffInitial = 1s` = `minReconnectInterval`), и без drain-гарда на новых RPC
агент успевает переоткрыть `Subscribe` внутри grace — одноразовый `CloseAllSubscribers` его уже не
закроет.

### Идея C — «хаб владеет контекстами стримов»

`AuthStreamInterceptor` оборачивает `ServerStream` и отдаёт хендлеру контекст, производный от
shutdown-контекста хаба.

**Атака (принята, идея снята):** (1) отмена производного контекста не разблокирует `Send` —
транспорт про обёртку не знает, `writeQuota` инициализируется закэшированным `s.ctxDone`;
(2) отменить RPC со стороны сервера, не закрывая транспорт, в grpc-go нельзя; (3) при отменённом
контексте обе ветки `select` в `server.go:210-222` готовы одновременно и часть `DeviceOffline`
теряется случайным выбором Go — у закрытого канала этой проблемы нет; (4) дублирование владения
подписками с Registry (#69).

**Ответ:** идея снята без спора. Её п.3 — прямой аргумент ЗА закрытие каналов, п.1 — за жёсткий
предел. Из неё в решение перешла ровно одна мысль: место для drain-гарда на новых RPC — это
интерцептор.

### Чем закончилось

Ни один подход не выживает в одиночку, и провалы у них разные: **два независимых режима
залипания**.

| Режим | Чем лечится | Чем НЕ лечится |
|---|---|---|
| хендлер в `select`: канал открыт, контекст стрима жив — это ОБЫЧНЫЙ случай, включая здорового агента (29.99 с) | закрытие канала подписчика | таймером: он добьёт то, что можно было закрыть штатно за 11 мс |
| хендлер в `stream.Send`: исчерпано окно flow control (мёртвый пир) | только закрытие транспорта (`Stop()`) | закрытием канала: хендлер не в `select` |

Решение — **синтез A+B**: закрытие подписок делает штатный путь достижимым и быстрым,
ограниченный по времени stop даёт верхнюю границу. Плюс обязательные следствия, без которых фикс
ломает сам себя: drain-гард на новых RPC (иначе реконнект-шторм переоткрывает подписки), `os.Exit`
по исчерпанию бюджета (иначе граница фиктивна), массовый свип (иначе бюджет тратится на
`busy_timeout`), явное состояние жизненного цикла и ожидание `Stop` в `cmd`.

**Отвергнутые альтернативы:**

- *Полагаться на серверный keepalive (#72).* Не срабатывает, пока клиент шлёт кадры; в лучшем
  случае 20 секунд при бюджете 10.
- *`MaxConnectionAge`/`MaxConnectionAgeGrace`.* Рвёт ЗДОРОВЫЕ соединения в обычной работе ради
  ускорения выключения. Цена несопоставима.
- *Новое событие протокола `HubShuttingDown`.* Правка `proto/` и обработчика в `internal/agent/**`
  (чужой скоуп, #77); старые агенты его всё равно не понимают. Роль «хаб уходит» играет связка
  `DeviceOffline` + чистое завершение стрима + `Unavailable` на следующем RPC.
- *`grpc.WaitForHandlers(true)`.* Выглядит как решение, даёт неограниченное ожидание.
- *Закрывать store при исчерпании бюджета.* После форсированного `Stop()` хендлеры живы
  (`server.go:1985`), и закрытие даёт им `sql: database is closed` вместо чистого разрыва. WAL
  включён, коммиты уже на диске — незакрытая база восстанавливается при следующем открытии.

**Вынесено в отдельные issue (не делать здесь):**

- Транзакционность `Join` и `ConfirmPairing` (`registry.go:60-90`, `pairing.go:111-121`): сейчас
  это 3-4 отдельные записи, и обрыв между ними оставляет потраченный токен, созданную строку и
  недоставленный сертификат (`certKeyBits = 2048`, генерация p50 49 мс / max 228 мс — на ARM SBC
  запаса нет). Реальный дефект, но не #75.
- Форма отказа `ErrHubShuttingDown` на уровне ответа (`Success=false` + строка вместо gRPC-статуса)
  — пересекается со скоупом #77. Здесь только фиксируем взаимодействие: **фикс #75 переводит
  частоту этого лога из 0 в 1** (сегодня стрим не завершается до смерти процесса, поэтому агент
  просто не успевает переподключиться; после закрытия подписок он переподключается сразу). Именно
  поэтому drain-гард ставится в интерцептор: он отвечает `codes.Unavailable` gRPC-статусом ДО
  хендлера, и `Success=false`-путь в этом окне не достигается.

## Solution Overview

Весь shutdown живёт под ОДНИМ дедлайном, а не под четырьмя последовательными: каждая фаза
получает остаток общего бюджета. Четыре независимых таймаута складываются, и сумма вылезает за
10 секунд `SignalStop` ровно в том случае, ради которого всё и делается.

`Hub.Start` начинается с **реконсиляции статусов**: один `UPDATE devices SET status='offline'
WHERE status='online'` до начала обслуживания. Это не отдельное улучшение, а то, что делает
ограниченный по времени свип корректным: у усечённого свипа появляется страховка, и «строка
осталась online» перестаёт быть фантомом, который переживает рестарт. Сегодня этой страховки нет
вовсе — при SIGKILL, OOM или потере питания свип не отрабатывает, а первый `checkStale` отстоит
на `timeout/3` ≈ 10 секунд, в течение которых хаб раздаёт пирам online-строки мёртвых устройств.

`Hub.Stop` становится последовательностью с гарантированной верхней границей:

1. `Drain()` — как сейчас (#69), плюс с этого момента интерцепторы отвечают `Unavailable` на
   любой новый RPC, включая `Subscribe` и `Join`: это защита от реконнект-шторма, который
   порождает шаг 4, и от сожжённого одноразового токена.
2. Отмена фоновых горутин хаба (heartbeat-монитор, свипер join-токенов).
3. Свип: `ListOnlineDevices` (одно чтение) → **ОДИН** `UPDATE devices SET status='offline'
   WHERE status='online'` → и только ПОТОМ broadcast `DeviceOffline` по каждому устройству.
   Порядок обратный нынешнему и он обязателен: под ограниченным контекстом обрыв между двумя
   шагами должен оставлять «строка offline, событие не доставлено» (пир заметит сам, по своему
   таймауту), а не «событие доставлено, строка online» — последнее и есть фантом из #69.
4. `CloseAllSubscribers()` — каждый `Subscribe` штатно завершается, предварительно доотдав
   буферизованные события свипа; клиент сам рвёт соединение на первом GOAWAY.
5. `GracefulStop()` в горутине; по истечении grace — `Stop()` тоже в горутине.
6. Ожидание фоновых горутин на остатке бюджета, затем `store.Close()` — **только если
   `GracefulStop` завершился сам**. Условие именно такое, а не «уложились в бюджет»: после
   форсированного `Stop()` хендлеры остаются ЖИВЫМИ (`server.go:1985`) независимо от того,
   вернулся форс внутри бюджета или нет, и закрытие базы дало бы им `sql: database is closed`
   вместо чистого разрыва — ровно то, что отвергнуто ниже. Поэтому `StopServer` сообщает **три**
   исхода, а не булево: graceful завершился / форс вернулся / не вернулся даже форс.
7. Если не вернулся даже форс (третий исход) — `Hub.Stop` сообщает об этом, и `cmd` удаляет
   pid-файл и делает `os.Exit(1)`. Во втором исходе процесс тоже выходит немедленно, но штатным
   путём и с кодом 0: живые хендлеры умирают вместе с процессом, а их коммиты уже на диске (WAL).

`cmd/hubfuse-hub` дожидается конца этой последовательности перед выходом из `RunE` и не
проглатывает повторный сигнал: сегодня `sigCh` читается ровно один раз, поэтому второй SIGTERM по
зависшему хабу не делает ничего — оператору остаётся только `kill -9`.

## Technical Details

### Drain-гард на новых RPC

- Интерцепторы (unary и stream) после `Drain()` возвращают `common.ErrHubShuttingDown` — он уже
  `status.Error(codes.Unavailable, ...)` (`common/errors.go:21`), то есть агент получает
  честный gRPC-статус, а не `Success=false` со строкой.
- Ставятся в цепочку ПЕРЕД auth-интерцепторами: уходящему хабу не важно, кто стучится.
- **Механика обязательна к соблюдению:** `grpc.UnaryInterceptor`/`grpc.StreamInterceptor`
  ПАНИКУЮТ при повторной установке (`grpc@v1.79.3/server.go:471-478`, `:492-499` —
  `panic("The unary server interceptor was already set and may not be reset.")`), а
  `serveropts.go:39-40` уже ставит оба. Поэтому обе строки ЗАМЕНЯЮТСЯ на
  `grpc.ChainUnaryInterceptor(drainUnary, AuthUnaryInterceptor)` и
  `grpc.ChainStreamInterceptor(drainStream, AuthStreamInterceptor)`: порядок в цепочке = порядок
  выполнения, что заодно и даёт требуемое «drain раньше auth». Добавить второй
  `grpc.UnaryInterceptor` в тот же слайс — это паника на `grpc.NewServer` и в проде, и во всём
  `hubtest`.
- `ServerOptions` принимает `*Registry` (нужен доступ к состоянию draining) — сигнатура меняется в
  обоих местах сборки сервера (`hub.go`, `hubtest.go`), что и есть смысл этого хелпера.
- Гард в интерцепторе — «дешёвый ранний выход»; авторитетный гард живёт в `Registry.Subscribe`
  внутри той же критической секции, где вставляется канал (иначе подписка, проехавшая между
  проверкой и вставкой, откроет стрим уже после `CloseAllSubscribers`). Это ровно паттерн
  `markOnlineUnlessDraining` из #69.

### Закрытие подписок

- `CloseAllSubscribers()` берёт write-lock и в ОДНОЙ критической секции делает `delete` + `close`
  по каждой записи. `delete` обязателен: `unsub` сравнивает идентичность канала
  (`registry.go:508`), а `Subscribe` при переподключении закрывает старый канал — вариант
  «позакрывать, очистить потом» даёт `close of closed channel`.
- Порядок «свип, потом закрытие» обязателен и безопасен: приём из закрытого буферизованного канала
  сначала отдаёт весь буфер и только потом `!ok`.
- `Subscribe` получает третье возвращаемое значение `error`; на пути отказа возвращается **не
  `nil`, а no-op `unsub`** — `server.go` делает `defer unsub()`, и `nil` там паникует.
- Инвариант #69 «`device_id` в `r.subscribers` == живая подписка» сохраняется: draining-хаб просто
  не заводит новых записей, а `canRecover`/`recoverAndAnnounce` и так отказывают при draining.

### Границы, бюджет и выход

- Общий бюджет: `Hub.Stop` берёт один дедлайн на всё (`DefaultShutdownBudget`, 6 секунд) и
  раздаёт остаток каждой фазе. Числа выбраны так, чтобы сумма гарантированно помещалась в
  10 секунд `SignalStop` вместе со свипом, который в худшем случае ждёт `busy_timeout = 5000`.
  Константа **экспортируется**: сценарный харнесс (`helpers.Hub`) обязан ждать дольше бюджета
  хаба, и второй захардкоженный литерал там неминуемо разъедется с этим.
- `hub.StopServer(srv, grace, logger) StopOutcome` — общий хелпер для `Hub.Stop` и `hubtest`,
  по образцу `ServerOptions`. Оба вызова (`GracefulStop` и `Stop`) — из горутин: каждый из них
  блокируется на ожидании соединений, и синхронный форс съел бы бюджет. Исходов ровно три —
  `StopGraceful` (graceful завершился сам), `StopForced` (не завершился, форс вернулся),
  `StopHung` (не вернулся даже форс); на них же завязаны три unit-теста Task 4 и решение о
  `store.Close()`.
- grace = 3 секунды. Обоснование пишется комментарием в коде (репозиторий документирует несущие
  транспортные константы, см. `serveropts.go`): grace меньше захардкоженного 5-секундного таймера
  grpc между двумя GOAWAY (`http2_server.go:1417`) — то есть мёртвое соединение форсируется
  раньше, чем grpc успеет за него заплатить. Верхняя рамка — 10 секунд `SignalStop` до SIGKILL,
  внутри которых должны поместиться ещё свип и закрытие store. Ручки в CLI/KDL нет: это не
  операторская настройка, а внутренний инвариант остановки — поэтому grace и бюджет живут
  **пакетными константами рядом с `serverKeepaliveTime`**, а НЕ полями `hub.Config`: `Config`
  заполняется из флагов Cobra (`cmd/hubfuse-hub/main.go:110-125`), то есть поле там — это и есть
  та самая ручка, которой быть не должно.
- `store.Close()` вызывается **только при `StopGraceful`** (см. отвергнутые альтернативы): при
  `StopForced` хендлеры живы ровно так же, как при `StopHung`, и разница лишь в том, вернулся ли
  форс.
- `Hub.Stop` возвращает признак «не уложились»; `cmd` в этом случае удаляет pid-файл ЯВНО (при
  `os.Exit` отложенные функции не выполняются) и делает `os.Exit(1)`.

### Жизненный цикл `Hub`

- Явное состояние под мьютексом (`не запущен` / `запущен` / `остановлен`), а не голая
  `WaitGroup`: `Stop` до `Start` обязан привести к тому, что `Start` НЕ начнёт обслуживание, иначе
  `Serve` поднимется поверх закрытого store.
- Проверка состояния стоит **до `net.Listen` и до `OnReady`**. `OnReady` пишет pid-файл
  (`cmd/hubfuse-hub/main.go:120-124`); хаб, который отказался обслуживать, но оставил pid-файл,
  заставит следующий `hubfuse-hub start` сказать «hub already running». Отказ `Start` — это
  чистый возврат (nil), а не ошибка запуска.
- `Start` заводит производный контекст и `WaitGroup` на фоновые горутины; `Stop` отменяет их до
  свипа и ждёт на остатке бюджета перед `store.Close()`.
- `Stop` идемпотентен (`sync.Once`) и **кэширует исход**: повторный вызов возвращает тот же
  `StopOutcome`, что и первый, а не нулевое значение — иначе у теста «двойной `Stop`» нет
  определённого ожидания, а второй сигнал мог бы получить «не уложились» на успешно
  остановленном хабе. Сегодня повторный вызов ещё и закрывает store дважды.
- Нормальное завершение по сигналу обязано давать **нулевой** код выхода. Точная механика (её
  легко переврать): на штатном пути `Serve` возвращает **nil** — его defer блокируется на
  `<-s.done.Done()` (`server.go:885-892`), а ветка Accept при сработавшем `quit` возвращает nil
  (`server.go:947-949`). `grpc.ErrServerStopped` появляется ТОЛЬКО когда `Serve` вызван уже после
  остановки (`server.go:878-882`). Ни один из двух путей нельзя раскрасить как ошибку запуска —
  иначе systemd будет видеть падение на каждом штатном `stop`.
- Повторный сигнал не проглатывается: обработчик читает `sigCh` в цикле, и второй SIGTERM,
  пришедший во время затянувшейся остановки, немедленно доводит процесс до `os.Exit`.
- Фоновые задачи хаба перестают логировать `context.Canceled` как Error/Warn — иначе каждое
  штатное выключение печатает ошибки. Это не только `checkStale` (`heartbeat.go:110`, `:123`):
  тот же отменённый контекст доходит до `pruneInactive` (`heartbeat.go:145`, уровень Error),
  `DeleteExpiredInvites` (`heartbeat.go:96`) и свипера join-токенов (`hub.go:136`). Лечится один
  раз общим хелпером, а не точечно в `checkStale`.

### Тестовая инфраструктура

- `hubtest` останавливается тем же путём, что прод (`Drain` → `CloseAllSubscribers` →
  `StopServer`), иначе фикс не доедет до тестов и харнесс продолжит зависеть от того, что
  `GracefulStop` вернётся сам.
- Реле (`tests/testrelay`) воспроизводит только режим «хендлер в `select`»; режим «хендлер в
  `Send`» проверяется unit-тестом на фейковом сервере, а не попыткой пропихнуть 64 КБ через реле —
  такой тест был бы флаки и ничего бы не доказывал.
- Интеграционный тест поднимает НАСТОЯЩИЙ `hub.NewHub`/`Start`/`Stop`, потому что предмет
  проверки — сам `Hub.Stop`. Две механики, которые иначе придётся выяснять на месте: (а) `Hub` не
  публикует адрес слушателя, поэтому порт выбирается заранее — `tests/integration` не импортирует
  `tests/scenarios/helpers`, так что нужен локальный аналог `FreePort` (пять строк на
  `net.Listen("tcp", "127.0.0.1:0")`); (б) `hub.NewHub` не отдаёт CA, поэтому клиентский
  сертификат тест выпускает сам — читает `dataDir/tls/ca.crt` + `ca.key` и зовёт
  `common.SignClientCert`, ровно как это делает `hubtest.loadOrCreateCA`.
- Сценарный харнесс: `helpers.Hub.Stop` сегодня ждёт 5 секунд и добивает `Kill` — это МЕНЬШЕ
  бюджета остановки (6 с). Сделать SIGKILL видимым, не подняв это ожидание, значит превратить
  штатный «путь для мёртвого пира» в падение на ровном месте, причём в `t.Cleanup` КАЖДОГО
  сценарного теста (`helpers/hub.go:94`). Ожидание выводится из экспортированной
  `hub.DefaultShutdownBudget` с запасом, а не вторым литералом.
- Сценарный тест определяет факт выхода через `cmd.Wait()` харнесса (харнесс — родитель процесса)
  и там же проверяет код выхода 0 — другого места для этой проверки нет. `helpers.Hub.Stop`
  поглощает `cmd.Wait()` и обнуляет `h.cmd` (`helpers/hub.go:127-143`), поэтому наблюдать
  «вышел сам, за сколько, с каким кодом» нужно новым хелпером (`SignalAndWait`), а не переиспользуя
  `Stop`. Ловушка, которую нельзя повторить: `kill(pid,0)` на зомби возвращает nil, поэтому
  «проверить сигналом» здесь нельзя. Тот же нюанс объясняет, почему `daemonize.waitForExit`
  корректен только для не-родителя.

### Task 6: `cmd/hubfuse-hub` дожидается остановки

Форма важнее формулировки: пока `stop()` не завершился, главная горутина СТОИТ в `Serve`
(`server.go:885-892`), поэтому «`RunE` ждёт `h.Stop()`» буквально невозможно — на исходе `StopHung`
`RunE` не получит управление никогда. Отсюда единственная рабочая раскладка:

- [x] сигнальная горутина зовёт `h.Stop()` сама; на `StopHung` она же удаляет pid-файл и делает
      `os.Exit(1)` (отложенные функции при `os.Exit` не выполняются); иначе закрывает `done`
- [x] `Serve` возвращается → `Start` возвращается → `RunE` ждёт `done` (только если сигнал был) и
      возвращает nil
- [x] повторный сигнал не проглатывается (чтение `sigCh` в цикле) и немедленно завершает процесс
- [x] штатная остановка по сигналу даёт код выхода 0: `Serve` на этом пути возвращает **nil**, а
      `grpc.ErrServerStopped` бывает только при `Serve` после остановки — ни то, ни другое не
      красится в ошибку запуска
- [x] тест: путь без сигнала не ждёт ничего (ошибка `listen` возвращается сразу)
