# Issue #78: новый агент против старого хаба — `GOAWAY too_many_pings` и цикл переподключений ~30 с

## Overview

С момента #72 агент дозванивается до хаба с `keepalive.ClientParameters{Time: 10s, Timeout: 5s,
PermitWithoutStream: true}` (`internal/agent/client.go`, `dialOptions`). Это законно только потому,
что современный хаб опускает `keepalive.EnforcementPolicy.MinTime` до 5 секунд
(`internal/hub/serveropts.go`). Хаб и агент ставятся отдельно, поэтому связка «новый агент против
хаба старее #72» физически возможна.

Issue утверждает: против старого хаба (дефолт grpc-go `MinTime: 5m`) каждый пинг агента —
нарушение, после третьего хаб шлёт `GOAWAY too_many_pings` и рвёт соединение, агент
переподключается, и так по кругу примерно раз в 30 секунд; каждый круг рассылает `DeviceOnline`
всем пирам, которые перемонтируют шары.

**Измерение опровергает это утверждение в том виде, в каком оно сформулировано.** Реальный демон
против реального хаба без `KeepaliveEnforcementPolicy` (то есть с наказывающим дефолтом grpc-go)
прожил 5 минут без единого разрыва:

| Что мерялось (окно 5 мин, продовые тайминги) | Значение |
|---|---|
| сессий установлено | **1** (на 628 мс), переустановок — **0** |
| `GOAWAY` / `too_many_pings` в логах grpc-go | **0** |
| heartbeat'ов | 29, все успешные |
| замен соединения (`dialFn`, «replaced the hub connection») | **0** |
| CPU за всё окно | **0.103 с** (≈0.03 %), пик 5.2 мс/с |
| горутины | 19 → 19, максимум 21 |

Строк лога от демона за 300 секунд ровно одна — `registered with hub`. Ни `hub session lost`, ни
`heartbeat failed`. Внутренний лог самого grpc-go (`GRPC_GO_LOG_SEVERITY_LEVEL=info`,
`VERBOSITY_LEVEL=2`), который печатает каждый PING и каждый GOAWAY, между установкой соединения и
концом окна **не содержит ни одной строки** — то есть агент не отправил ни одного пинга.

Причина — две независимые подавляющие силы, обе подтверждены по исходникам grpc-go v1.79.3:

1. **Клиент не пингует, пока идут чтения.** Горутина keepalive шлёт PING только если на транспорте
   не было чтений в течение `Time`. Heartbeat агента раз в 10 секунд двигает `lastRead` ровно с той
   же частотой, поэтому таймер пинга бесконечно перевзводится и не срабатывает.
2. **Сервер обнуляет счётчик страйков на каждой своей записи.** `setResetPingStrikes` подвешен как
   `onWrite`/`onEachWrite` на заголовки, данные и трейлеры ответа
   (`http2_server.go:1042`, `:1110`, `:1154`), а `handlePing` делает
   `CAS(resetPingStrikes, 1, 0) → pingStrikes = 0` (`:891-893`). Ответ на каждый heartbeat обнуляет
   страйки, а для GOAWAY нужно **три подряд** (`maxPingStrikes = 2`, условие `> maxPingStrikes`,
   `:911-914`).

Обе силы требуют одного и того же — **живого heartbeat'а**. Отсюда переформулировка issue:
наказание требует ПРОСТАИВАЮЩЕГО соединения, а не просто старого хаба. Совместимость с хабом
старее #72 у нас сегодня есть — но она **случайна**: её не фиксирует ни один тест, и держится она
на негласном соотношении между кадансом heartbeat'а и интервалом keepalive.

Гипотеза о связи с #73 (соединение в `draining` крутит `NewStream` в плотном цикле и жжёт ~180 %
CPU) **также не подтвердилась** — ни по исходникам, ни измерением. Подробности ниже.

## Context (from discovery)

**Проверено по исходникам grpc-go v1.79.3** (модуль из `go.mod`, читался из `GOMODCACHE`):

- `internal/transport/http2_server.go:911-914` — GOAWAY по too_many_pings уходит на **третьем**
  нарушающем пинге (`maxPingStrikes = 2`, условие `pingStrikes > maxPingStrikes`). Это ОДИН GOAWAY
  с выставленным `closeConn`; TCP закрывается не позже чем через ~1 секунду
  (`HandleStreams`, `:342-361`), а не после второго GOAWAY, как в graceful-пути `Drain()`.
- `internal/transport/defaults.go:40` — `defaultKeepalivePolicyMinTime = 5 * time.Minute`, тот самый
  порог старого хаба. `defaults.go:36` — `defaultServerKeepaliveTime = 2 * time.Hour`, то есть
  **до-#72 хаб сам пингов практически не шлёт**.
- `http2_server.go:898-909` — `PermitWithoutStream` выбирает ПОРОГ, а не включает проверку: при
  `ns < 1` и `PermitWithoutStream=false` пинг сравнивается с `defaultPingTimeout = 2h`, поэтому
  почти любой пинг без открытого стрима — страйк.
- `http2_server.go:1042`, `:1110`, `:1154` + `:271-273` + `:891-893` — счётчик страйков обнуляется
  на КАЖДОЙ записи сервера (заголовки/данные/трейлеры ответа). Это второй подавитель.
- `internal/transport/http2_client.go:1334-1340` — при `ErrCodeEnhanceYourCalm` + debug data
  `"too_many_pings"` клиент пишет через `logger = grpclog.Component("transport")`
  (`internal/transport/logging.go:28`) строку:
  `Client received GoAway with error code ENHANCE_YOUR_CALM and debug data equal to ASCII "too_many_pings".`
- `http2_client.go:1363-1374` — далее `setGoAwayReason`, `close(t.goAway)`, `t.onClose(reason)` и
  только ПОТОМ `t.state = draining`. Порядок важен (см. ниже про #73).
- **Причина GOAWAY доступна прикладному коду — но не через типизированный аксессор, а строкой.**
  Здесь план был ИСПРАВЛЕН по ходу работы, и исправление важнее исходного утверждения (см.
  «Итоги plan-review», добавление от 2026-08-17). Первоначально было записано, что причина не
  выходит за пределы `internal/transport`, а значит пункт 1 из issue неверен. **Это оказалось не
  так, и опровергло его собственное измерение проекта:** стрим, живой на транспорте в момент его
  закрытия, получает статус, в текст которого вшита debug data GOAWAY. Наблюдено в интеграционном
  тесте дословно:

  ```
  rpc error: code = Unavailable desc = closing transport due to: connection error:
  desc = "error reading from server: EOF", received prior goaway:
  code: ENHANCE_YOUR_CALM, debug data: "too_many_pings"
  ```

  Механизм по исходникам: `http2_client.go:1417-1419` кладёт
  `fmt.Sprintf("code: %s, debug data: %q", f.ErrCode, f.DebugData())` в `goAwayDebugMessage`, а
  `:1052-1053` подставляет его в статус, который рассылается ВСЕМ активным стримам при закрытии
  транспорта. Верно лишь то, что **типизированная** причина недоступна: `GetGoAwayReason` живёт в
  `internal/transport` и вызывается только тестами самого grpc-go.

  **Практическое следствие:** пункт 1 из issue («сматчить причину в тексте ошибки») — рабочий и
  дешёвый путь, без процессного глобала. Подстрока `too_many_pings` приходит ОТ СЕРВЕРА (это
  debug data кадра GOAWAY, `http2_server.go:913`), поэтому она зафиксирована во всех уже
  выпущенных старых хабах; меняться со временем может обёртка grpc-go вокруг неё, но не она сама.
  Именно поэтому интеграционный тест ассертит эту подстроку — обновление grpc-go, переставшее
  доносить debug data, обязано ломать сборку, а не выключать детект молча.
- `clientconn.go:1302-1313` (`adjustParams`) — на `GoAwayTooManyPings` клиент **удваивает**
  `cc.keepaliveParams.Time`, монотонно и на весь `ClientConn`; `clientconn.go:1452-1455`
  перечитывает это значение перед созданием КАЖДОГО нового транспорта. То есть наказание
  самозатухает (10→20→40→80→160→320 с), а сбрасывает адаптацию только НОВЫЙ `ClientConn`.
- `http2_client.go:826-866`, `:881-905` — в draining-ветке `checkForStreamQuota` делает
  `t.streamQuota--` (`:840`) ДО проверки `t.state == draining` (`:843-845`) и уходит, не вернув
  квоту: `executeAndPut` не ставит `hdr` в очередь, поэтому `onOrphaned` не зовётся, а
  `addBackStreamQuota` работает только из `closeStream`. Утечка квоты реальна — но **цикла нет**:
  `t.goAway` закрыт до установки `draining`, поэтому `select` на `:896-905` немедленно отдаёт
  `errStreamDrain` (`AllowTransparentRetry: true`), без повторного круга.
- `http2_client.go:271` — `isyscall.SetTCPUserTimeout(conn, kp.Timeout)`: `TCP_USER_TIMEOUT` ядра
  взводится из keepalive `Timeout`. Ослабление keepalive снимает и эту защиту.

**Измерено.** Все прогоны — реальные сокеты, реальный mTLS, продовый gRPC-стек, фикстура хаба
собрана поверх `hub.ServerOptions` с единственным отличием (см. Technical Details). Позитивные и
негативные контроли обязательны и присутствуют: без B1 «зелёный» прогон 1 не доказывал бы ничего —
он одинаково зелен и когда наказания нет, и когда фикстура вообще не умеет наказывать.

|---|---|---|

Из этой таблицы следуют три вывода, на которых стоит весь фикс:

1. **Наказание требует простоя порядка трёх интервалов keepalive подряд без записи сервера.** B1
   даёт GOAWAY на 30.07 с (3 × 10 с), B3 при кадансе 10 с не даёт его никогда.

   **Оговорка, которую нельзя замазать (найдена на plan-review).** B2 измерил НЕ установившийся
   режим при кадансе 40 с: GOAWAY там пришёл на 30.38 с, то есть ВНУТРИ первого простаивающего
   окна, ещё до первого удара сердца. Значит B2 — это повтор B1, а не точка на границе. Эмпирически
   покрыты только каданс = `T` (B3, зелено) и полный простой (B1/B2, GOAWAY на 3T); интервал
   `(T, 3T]` не измерен вовсе. Поэтому Task 1 добавляет третье соединение с кадансом `2.5T`, чтобы
   граница перестала быть выводом из механики и стала измерением.

   **Модель не сходится с измерением, и это записано честно.** `handlePing` при
   `CAS(resetPingStrikes, 1, 0)` обнуляет счётчик и делает **ранний `return`**
   (`http2_server.go:891-894`) — то есть первый пинг после любой записи сервера действительно
   «бесплатный». Отсюда наивная модель предсказывает страйки на 2-м, 3-м и 4-м пингах и GOAWAY на
   **4T = 40 с**, а измерено 30 с, дважды и независимо. Разница в один интервал НЕ объяснена.
   Рабочая гипотеза (проверялась по исходникам, но не измерялась): «бесплатный» сброс съедает не
   keepalive-пинг, а BDP-пинг клиента (`internal/transport/bdp_estimator.go`), который сервер в
   `handlePing` никак не выделяет. **Инвариант ведём от измеренного 3T как от консервативного
   значения**, а не от модельного 4T: ошибиться в сторону запаса безопасно, в обратную — нет.
2. **TCP-keepalive не заменяет HTTP/2-пинг** (C1 против C2: «никогда» против 15.009 с на одном и том
   же разрыве). Причина в `testrelay.Break()`: реле продолжает читать и выбрасывать байты
   (`relay.go:92-105`), поэтому ядро подтверждает и TCP-пробы тоже. C1 — это дословно тот отказ,
   ради которого делался #72.
3. **Механизм из комментария к #73 не воспроизводится даже в самом сильном варианте** — когда
   транспорт удерживается в `draining` открытым стримом 25 секунд подряд (D).

**Остаточная цена наказания, которую сегодня никто не видит.** B1 показывает, что соединение
чинится само за 7 мс, то есть прикладного отказа нет. Но `adjustParams` при каждом GOAWAY
**удваивает** `cc.keepaliveParams.Time` этого `ClientConn` монотонно и навсегда. То есть каждое
наказание молча ослабляет ровно ту защиту, которую добавил #72, и об этом не сообщается никак:
причина GOAWAY до прикладного кода не доходит вообще. Это и есть содержательное обоснование
диагностики (Task 3), а не «улучшить лог».

**Почему #73 не подтверждается механизмом из комментария к issue.** `t.onClose(reason)` вызывается
на `:1371` ДО `t.state = draining` на `:1372`, а `onClose` (`clientconn.go:1486-1509`) обнуляет
`ac.transport` и переводит addrConn в `Idle`. Поэтому к моменту прозрачного ретрая пикер физически
не может выдать тот же draining-транспорт — новый стрим уходит на свежий. Измерение это
подтверждает: grpc-go сносил и заменял draining-транспорт в пределах той же секунды на каждом из
пяти циклов.

**Код репозитория:**

- `internal/agent/client.go:35-38` — `hubKeepaliveTime = 10s`, `hubKeepaliveTimeout = 5s`; одна
  точка (`dialOptions`) на оба дозвона.
- `internal/agent/heartbeat.go:12` — `defaultHeartbeatInterval = 10s`, переопределяется
  `HUBFUSE_HEARTBEAT_INTERVAL` (`heartbeatIntervalFromEnv`) без верхней границы.
- `internal/agent/daemon.go:828-829` — `defaultRegisterTimeout`/`defaultSubscribeSetupTimeout` = 20 с;
  `internal/agent/bounds_test.go:44` фиксирует
  `hubKeepaliveTime + hubKeepaliveTimeout (15s) < defaultRegisterTimeout (20s)`.
- `internal/agent/daemon.go:841-876` — `errSessionTimedOut` / `ourBudgetExpired`: замена соединения
  происходит ТОЛЬКО когда истёк НАШ дедлайн. Комментарий на `:852-855` утверждает, что «в
  draining-после-GOAWAY каждый вызов возвращает `Unavailable`, а падает по дедлайну вызывающего».
  Для чистого цикла наказания это не так: старый хаб закрывает TCP примерно через секунду после
  GOAWAY, поэтому вызовы падают быстрым `Unavailable`, наш бюджет не истекает, и `replaceHubClient`
  не вызывается — что и подтверждено нулём замен в прогоне 1.
- `internal/agent/connector.go:17-18` — `backoffInitial = 1s`, `backoffMax = 60s`.
- **`CLAUDE.md` и `internal/hub/serveropts.go:17-21` утверждают, что «агент с v0.1.3 против более
  старого хаба разрывается по циклу ~30 с». Измерение это опровергает — документация обязана быть
  исправлена в этой же ветке.**
- Ни одной строки с `grpclog` в репозитории сегодня нет; операторской документации про порядок
  обновления нет (`.goreleaser.yaml:56-57` — `changelog: use: github-native`, CHANGELOG отсутствует,
  единственное упоминание порядка — в `CLAUDE.md`, файле для ИИ-агентов, а не для оператора).

## Итоги брейншторма и дебатов

Рассматривались четыре принципиально разных подхода; на каждый заводился отдельный агент-критик с
ролью жёсткого оппонента, по три полноценных раунда (идея → атака → ответ и контратака → ответ
критика). Пятая идея возникла по ходу и была снята до дебатов. Ниже — суть.

### Идея 1 — «только диагностика»

Мост `grpclog.SetLoggerV2` в бинаре агента, одноразовый матчер на строку `too_many_pings`, один
Error с действием («хаб слишком стар — обнови хаб»). Поведение транспорта не меняется, удвоение
grpc-go само доводит интервал до приемлемого.

**Атака:** (1) история про сходимость не проверена — если `reconnectSession` заменит `ClientConn`,
удвоение сбрасывается и цикл становится вечным; (2) диагностика без действия оставляет шторм
перемонтирований; (3) `grpclog.SetLoggerV2` — процессный глобал, а бинарь ещё и тестируется
in-process вместе с хабом; (4) уровень и объём логов не определены: на Info — шум, на Debug —
инструмент прячется от того, кто его ищет; (5) строка внутренняя, при обновлении grpc-go матчер
молча перестанет срабатывать; (6) «один раз за жизнь процесса» — не та гранулярность.

**Ответ:** (3)-(6) приняты и учтены в дизайне. Механизм из (1) опровергнут: старый хаб закрывает TCP
через ~1 с после GOAWAY, вызовы падают быстрым `Unavailable`, а `ourBudgetExpired` смотрит
исключительно на СВОЙ дедлайн — значит замены нет и удвоение выживает.

**Ответ критика (раунд 3):** переходный процесс хуже установившегося: путь 10→320 с — это ~620 с
наказаний, причём поздние интервалы (160 с, 320 с) каждый по отдельности длиннее 30-секундного
`DefaultHeartbeatTimeout` хаба, то есть устройство не «флапает», а сидит демотнутым минутами.

### Идея 2 — «детект и адаптация: безопасный keepalive»

То же обнаружение, но агент переходит в «режим старого хаба» и передозванивается с параметрами,
которые дефолтная политика терпит.

**Атака (принята, идея снята):** (1) ослабленный keepalive ломает зафиксированный порядок
`hubKeepaliveTime + hubKeepaliveTimeout < defaultRegisterTimeout` — обычные разрывы начинают
классифицироваться как `errSessionTimedOut` и жечь замену соединения на каждом сбое wifi;
(2) гонка: колбэк grpclog и `reconnectSession` борются за один CAS, и если побеждает обычная
замена, она передозванивается ТЕМИ ЖЕ наказуемыми параметрами; (3) «липучесть» — ложь, пока
`dialFn` не несёт безопасные параметры сам; (4) после апгрейда хаба агент остаётся деградированным
навсегда и молча.

**Добито измерением и исходниками:** `PermitWithoutStream: false` вводит keepalive-горутину в
спячку (`kpDormancyCond.Wait()`) — между сессиями не пингуется вообще ничего; а `Time` порядка 6
минут в 12 раз медленнее 30-секундного таймаута хаба, то есть детект бесполезен by construction.
Плюс `SetTCPUserTimeout` (`http2_client.go:271`) взводится из `Timeout`, и ослабление снимает
ещё и ядерную границу на неподтверждённые данные.

### Идея 3 — «версия/капабилити в `RegisterResponse`»

Хаб сообщает версию (или прямо `keepalive_min_time_ms`), агент выбирает параметры до наказания.

**Атака (принята, идея снята):** (1) это не проверка поля, а постоянный налог: на КАЖДУЮ сессию
против старого хаба — дозвон, Register, обнаружение нуля, закрытие, передозвон, повтор всего
незавершённого; (2) поле отвечает на вопрос «пересобрали ли хаб», а не «терпит ли его политика
быстрые пинги» — а они расходятся для хаба с #72, но без нового поля; (3) неоднозначность нуля не
рассасывается, а нарастает: как только #72 и #78 выйдут разными релизами, популяция «есть #72, нет
поля» непуста и неотличима от древнего хаба, и агент навсегда откажет в быстром keepalive хабу,
который его поддерживает; (4) «обобщается на будущие настройки» — обобщается как раз дорогой
midsession-передозвон.

### Идея 4 — «сделать keepalive агента универсально безопасным»

Убрать рассинхрон вместо диагностики: параметры, которые терпит любой хаб.

**Атака (принята, идея снята):** (1) собственная история проекта это опровергает — на v0.1.2
per-call дедлайны heartbeat'а (#69) уже были, и соединение всё равно висело `hub_conn=0` вечно до
ручного рестарта; (2) причина по исходникам: `keepalive()` по таймауту зовёт `t.Close(err)`,
который ставит `SetWriteDeadline`/`SetReadDeadline` на СОКЕТ — специально «на случай, если
соединение чернодырное, то есть TCP просто застрял», — и разом валит все активные стримы;
`context.WithTimeout` вокруг одного RPC не трогает общий транспорт и не расклинивает его для
следующего стрима; (3) `PermitWithoutStream: false` — не нейтрально, а спячка; (4) ломается
зафиксированный инвариант границ; (5) детект heartbeat'ом (~30 с) сравнивается с 30-секундным
таймаутом хаба — то есть агент теряет фору и сам начинает порождать `DeviceOffline`→`DeviceOnline`,
то самое перемонтирование, с которого #78 начинается.

### Идея 5 — «перенести детект на уровень TCP» (снята до дебатов)

`grpc.WithContextDialer` с `net.Dialer{KeepAliveConfig: {Idle, Interval, Count}}`: TCP-пробы —
это IP-уровень, они никогда не становятся HTTP/2-кадром, и наказать их нечем ни старому хабу, ни
новому.

**Почему снята:** TCP-keepalive шлётся только когда соединение **простаивает** — нет
неподтверждённых данных. Агент пишет heartbeat каждые 10 секунд, поэтому на чернодырном соединении
записи висят неподтверждёнными, ядро находится в режиме ретрансмиссии, а не keepalive, и детект
падает на RTO (минуты), а не на `Idle+Interval×Count`. Вдобавок `testrelay.Break()` — фикстура, на
которой #72 регрессируется, — продолжает ЧИТАТЬ и выбрасывать байты, поэтому ядро реле подтверждает
и TCP-пробы тоже: этот сценарий TCP-keepalive не ловит принципиально. Проверено измерением
(эксперимент C, см. Technical Details).

### Чем закончилось

Ни один из четырёх подходов не пережил дебаты в исходном виде, и измерение объяснило почему:
**все они лечат симптом, которого в установившемся режиме нет.** Наказание требует
простаивающего соединения, а у работающего демона соединение не простаивает никогда — heartbeat
подавляет его с обеих сторон сразу.

Отсюда честный вывод, который и лёг в решение: совместимость со старым хабом у нас **уже есть**, но
она **случайна и ничем не зафиксирована**. Фикс — не новый механизм, а превращение случайного
свойства в проверяемый инвариант плюс исправление документации, которая сегодня утверждает
неправду.

**Отвергнутые альтернативы (сводка):**

- *Латч «не заменять соединение, пока хаб наказывает».* Защищает от того, чего не происходит
  (замен ноль, измерено), а в редком случае «старый хаб + вдобавок чернодырное соединение» отнимает
  единственный рычаг восстановления (`replaceHubClient`) и воспроизводит до-#72-шный отказ
  «лечится только рестартом».
- *Ослабление keepalive в любом виде.* Снимает `t.Close()` с его дедлайнами на сокете, усыпляет
  keepalive-горутину (`PermitWithoutStream: false`), снимает `TCP_USER_TIMEOUT` и ломает
  зафиксированный порядок границ. Регресс #72 ради проблемы, которой в установившемся режиме нет.
- *Версия/капабилити в `RegisterResponse`.* Отвечает не на тот вопрос и вводит неоднозначность
  нуля, которая со временем только растёт.
- *TCP-keepalive вместо HTTP/2-пингов.* Пробы шлются только на ПРОСТАИВАЮЩЕМ соединении, а heartbeat
  каждые 10 секунд держит неподтверждённые данные — детект падает на RTO. Плюс `testrelay.Break()`
  продолжает читать и подтверждать байты (`relay.go:92-105`), поэтому TCP-пробы подтверждаются и
  разрыв не виден принципиально.
- *Трогать `keepaliveMinTime` на хабе.* Старые агенты шлют пинги раз в 10 секунд, и снятие
  послабления сломало бы их. Хаб в этой ветке не меняется вообще.

## Solution Overview

Фикс не добавляет механизма — он превращает случайно работающее свойство в проверяемое и
исправляет документацию, которая сегодня описывает несуществующее поведение. Четыре части:

1. **Зафиксировать совместимость.** Регресс-тест: реальный демон против реального хаба со СТАРОЙ
   политикой (`MinTime: 5m`) живёт окно без единого разрыва и без замен соединения. Обязателен
   **позитивный контроль** — простаивающее соединение против ТОЙ ЖЕ фикстуры обязано получить
   `GOAWAY too_many_pings`. Без него зелёный регресс-тест ничего не доказывает: он одинаково зелен и
   когда всё хорошо, и когда фикстура собрана неправильно и не наказывает вообще.

2. **Зафиксировать инвариант, на котором совместимость держится.** Она держится на соотношении
   каданса heartbeat'а и интервала keepalive, и сегодня это соотношение не записано нигде. Пин в
   `bounds_test.go` плюс предупреждение, если `HUBFUSE_HEARTBEAT_INTERVAL` выставлен в значение,
   которое инвариант ломает.

3. **Дать диагностику для остаточного случая.** Наказание требует простаивающего соединения, и в
   демоне такого окна нет — heartbeat идёт на контексте всей жизни демона. Но оно есть в CLI:
   `hubfuse join` дозванивается, делает `Join`, получает «nickname taken» и снова блокируется на
   `promptNickname` (`cmd/hubfuse/main.go:144-165`) — транспорт уже установлен, RPC не идут, человек
   думает над именем. Дольше ~30 секунд — и старый хаб рвёт соединение. Сегодня оператор не получает
   об этом НИКАКОГО сигнала: причина GOAWAY не доходит до прикладного кода вообще, а RPC падают
   обобщённым `Unavailable`. Единственный внешне наблюдаемый след — строка grpclog, поэтому мост
   `grpclog.SetLoggerV2` и есть тот самый «агент прямо говорит, что происходит» из issue.

4. **Исправить неправду в документации** и дать оператору заметку про порядок обновления.

Чего фикс НЕ делает и почему: не меняет параметры keepalive (это регресс #72), не заводит латч
(защищал бы от несуществующего), не трогает proto (отвечает не на тот вопрос) и не трогает политику
хаба (сломало бы старых агентов).

## Technical Details

### Фикстура «хаб до #72»

`grpc.KeepaliveEnforcementPolicy` — это простое присваивание в `serverOptions`
(`grpc@v1.79.3/server.go:335-339`), поэтому опция, добавленная ПОСЛЕ `hub.ServerOptions(...)`,
побеждает. Значит фикстура — это ровно одна дописанная опция поверх продовых:

```go
opts := append(hub.ServerOptions(creds, registry),
    grpc.KeepaliveEnforcementPolicy(keepalive.EnforcementPolicy{MinTime: 5 * time.Minute}))
```

Это эквивалентно тому, что делал хаб до #72 (не передавал политику вовсе — тогда `MinTime`
достаётся из `defaultKeepalivePolicyMinTime`, `http2_server.go:242-243`), но записано явно, поэтому
тест читается без знания дефолтов grpc-go. Всё остальное — креды, интерцепторы, реализация сервиса —
остаётся продовым, иначе тест проверял бы не тот транспорт.

### Сокращение окон невозможно — и это меняет форму тестов

Первая версия этого плана предлагала сделать `hubKeepaliveTime`/`hubKeepaliveTimeout` `var`'ами и
подменять их в тестах на сотни миллисекунд. **Это не работает, и хорошо, что проверено до кода:**
`grpc.WithKeepaliveParams` зажимает `Time` снизу десятью секундами —
`dialoptions.go:562-564`, `internal.KeepaliveMinPingTime = 10 * time.Second`, с комментарием «This
must be 10s by KeepAlive spec». Любое меньшее значение молча поднимается обратно до 10 секунд (с
предупреждением в лог grpc-go). Значит:

- окно до наказания принципиально равно `3 × 10 с ≈ 30 с` и НЕ сокращается со стороны клиента;
- со стороны сервера тоже нельзя: наказание считается по пингам клиента, а не по политике;
- следовательно, `hubKeepaliveTime` **не превращается в `var`** — правка была бы бесполезной, а
  мутация package-level state в тестах — лишним риском. Диффа меньше, инвариантов больше.

Отсюда двухуровневая стратегия вместо сокращения:

1. **Быстрый unit-тест на арифметику инварианта** (без сети вообще): именно он ловит регрессию,
   потому что ломает её изменение констант, а не поведение сети.
2. **Один медленный сквозной тест (~35 с) в `tests/integration`**, где окна такого порядка уже
   норма. Он ставит ОБА контроля в ОДНО окно и не нуждается ни в глобальном логгере, ни в
   подмене констант:

   на одном и том же старом хабе поднимаются ДВА соединения, у каждого открыт `Subscribe`:
   одно молчит, второе шлёт heartbeat раз в 10 секунд. Через ~35 секунд у молчащего стрим
   **обязан быть мёртв** (GOAWAY, затем хаб закрывает TCP примерно через секунду), у
   heartbeat'ящего — **жив**. Это A/B с позитивным и негативным контролем одновременно,
   атрибуция по соединению (а не по глобальному логу), и падает он ровно тогда, когда ломается
   проверяемое свойство.

### Инвариант, который держит совместимость

Два независимых подавителя (см. Context) требуют одного: сервер должен что-то писать чаще, чем
клиент успевает набрать три страйка. Отсюда:

- `defaultHeartbeatInterval <= hubKeepaliveTime` — клиент вообще не отправляет пинг, пока ответы
  heartbeat'а двигают `lastRead`. Это то, что наблюдается сегодня (ноль пингов за 5 минут).
- `heartbeatInterval < 3 * hubKeepaliveTime` — более слабое и более фундаментальное условие: даже
  если пинги пойдут, ответ heartbeat'а обнулит страйки раньше третьего.

Первое фиксируется тестом. Второе — граница, за которой совместимость ломается, и именно её может
перешагнуть оператор через `HUBFUSE_HEARTBEAT_INTERVAL`. Ручка НЕ клампится (сценарные тесты
ставят значения МЕНЬШЕ дефолта, и запрещать это нельзя), но значение `>= 3 * hubKeepaliveTime`
получает Warn с прямым текстом про старый хаб. Отдельно замечено и НЕ чинится здесь: любое значение
больше 30 секунд уже ломает liveness против ЛЮБОГО хаба (`DefaultHeartbeatTimeout` = 30 с), что
является более крупной проблемой этой ручки и относится не к #78.

### Мост grpclog

`grpclog.SetLoggerV2` — процессный глобал, и это его главное ограничение. Отсюда правила:

- ставится ТОЛЬКО в пути демона (`cmd/hubfuse/main.go`, `runDaemon`), под `sync.Once`, до создания
  любого gRPC-соединения; CLI-команды его не ставят;
- уровни: grpc Info/Warning → slog Debug, Error/Fatal → slog Warn. Иначе внутренняя болтовня
  grpc-go (резолвер, балансировщик, смены состояния подканала) попадёт оператору в Info. Сегодня
  дефолтный логгер grpc-go печатает на stderr только Error-уровень, так что мост не должен делать
  вывод шумнее, чем он есть;
- матчер срабатывает один раз за жизнь процесса и пишет ОДИН Error с действием;
- **строка матчится не по константе в тесте, а против настоящего сервера со старой политикой** —
  тест поднимает такой сервер, доводит простаивающее соединение до GOAWAY и требует, чтобы матчер
  сработал. Обновление grpc-go, поменявшее формулировку, ломает сборку, а не выключает детект молча.

Точный текст, который печатает grpc-go (`http2_client.go:1339`, через
`grpclog.Component("transport")`, то есть с префиксом `[transport]`):

```
Client received GoAway with error code ENHANCE_YOUR_CALM and debug data equal to ASCII "too_many_pings".
```

### Добавление от 2026-08-17: Task 3 восстановлен в другой форме

Уже ПОСЛЕ ревью, на приёмке Task 1, интеграционный тест напечатал ошибку умершего стрима, и в ней
дословно оказалось `debug data: "too_many_pings"`. Это опровергло собственное утверждение плана
(«причина недоступна прикладному коду»), на котором держалась и форма Task 3, и частично основание
её снятия. Цепочка зафиксирована целиком, потому что оба разворота — часть доказательства:

1. issue предлагал детект по тексту ошибки;
2. археология по исходникам сказала «нельзя, только строка grpclog» — и Task 3 был спроектирован как
   процессный мост `grpclog.SetLoggerV2`;
3. plan-review снял Task 3 — справедливо, но снял он ФОРМУ (глобал + установка не в том бинаре);
4. измерение показало, что детект возможен обычным `strings.Contains` по ошибке стрима, которую
   демон и так уже обрабатывает.

Поэтому Task 3 возвращается в форме **Task 3′**: ~5 строк в существующем пути обработки смерти
сессии, без глобального состояния, без нового бинарного пути. Все возражения ревью относились к
снятой форме и на новую не переносятся. Остаётся верным (и влияет на ТЕКСТ сообщения, а не на факт
его существования): при продовых настройках демон в это состояние не попадает, поэтому сообщение
обязано называть причину и действие, ничего не преувеличивая.
