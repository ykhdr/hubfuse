# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow

Always commit and push after completing an action (feature, fix, refactor, etc.) without waiting for explicit request.

**Plans move to `docs/plans/completed/` BEFORE the branch is merged, never after.** The move
belongs in the feature branch itself, as part of the work it documents — so the plan lands in
`completed/` in the same merge. Moving it afterwards costs an extra branch and PR for pure
housekeeping, and until that lands the repo contradicts its own plan docs. This applies to
every plan the branch completes, including any rework plan that superseded the original.

## Project

HubFuse is a network file sharing system for local networks. Devices mount remote directories transparently via SSHFS, coordinated by a central gRPC hub server. Written in Go 1.25.

## Build & Test Commands

```bash
make build              # go build ./...
make test               # run all tests (unit + integration)
make test-unit          # go test ./internal/...
make test-integration   # go test ./tests/integration/... -timeout 180s
make test-race          # go test -race ./internal/agent/... (not part of `make test`)
make vet                # go vet ./...
make proto-gen          # regenerate gRPC code from proto/hubfuse.proto
make install            # install hubfuse-hub and hubfuse to $GOPATH/bin
make release-snapshot   # build a local snapshot release with GoReleaser (no publish)
make release-check      # validate .goreleaser.yaml (goreleaser check)
```

Run a single test: `go test ./internal/hub/store/... -run TestName`

## Architecture

Hub-and-spoke model with two binaries:

- **hubfuse-hub** — Central gRPC server. Manages device registry, pairing, heartbeat monitoring, and event broadcasting. Stores state in SQLite (pure Go, no CGO via `modernc.org/sqlite`).
- **hubfuse** — Daemon running on each device. Connects to hub, exports local directories via an embedded SSH server, and mounts remote shares via SSHFS.

### Communication

All communication uses gRPC with mTLS. The proto definition is in `proto/hubfuse.proto`. Key flows:

1. **Join** (unauthenticated) — Device gets TLS client cert from hub
2. **Register** — Device announces shares/SSH port, receives online device list
3. **Subscribe** — Server-streaming RPC pushes events (DeviceOnline/Offline/SharesUpdated/PairingRequested/PairingCompleted)
4. **Pairing** — Two-step invite code exchange (RequestPairing → ConfirmPairing) to swap SSH public keys

Device identity is extracted from the mTLS certificate CN field via a gRPC interceptor (`internal/hub/interceptor.go`).

### Hub internals (`internal/hub/`)

- `hub.go` — Orchestrator that wires components and manages lifecycle. `lifecycleState` (not-started/started/stopped) is what lets `Stop` and `Start` each ask "did the other one already run" — a bare `sync.WaitGroup` cannot answer that: `wg.Wait()` on a WaitGroup nothing has ever `Add`'d to returns instantly, which is exactly what let a Stop-before-Start sequence close the store and then have `Start` bring a server up over it. `Start` checks the state on entry — ahead of `ReconcileDeviceStatuses` — and re-checks it once the listener is bound, before publishing the server and before `OnReady`, because `OnReady` is what writes the PID file and a hub that will not serve must not leave one behind. Everything `Start` runs before it can observe a concurrent `Stop` also filters its own error through `h.stopped()`: a cancelled context or a closed store reaching `ReconcileDeviceStatuses`, and `grpc.ErrServerStopped` reaching `Serve`, are a clean shutdown seen from an unlucky angle, and returning either as a startup failure makes systemd record a failed unit for an ordinary `hubfuse-hub stop`. `Stop`'s sequence runs under ONE `DefaultShutdownBudget` (6s), not one deadline per phase: Drain (refuse new online rows) → cancel the background goroutines → sweep online devices offline → `CloseAllSubscribers` → `StopServer` → wait for the background goroutines → `store.Close`, with `splitRemaining` handing each phase whatever time is left rather than a fresh clock. The sweep writes before it broadcasts; the reverse order is the #69 phantom ("event delivered, row still online" survives as a stale online row for the next hub start to serve). `ReconcileDeviceStatuses` at startup clears every online row unconditionally, which is what makes a sweep truncated by the budget — or skipped entirely after SIGKILL — safe to recover from. `stopResultFor` splits "settled" (finished inside the budget) from "may close the store": `StopForced` settles but must NOT close the store, because only the graceful path carries grpc-go's guarantee that every handler has already returned. The final wait for the hub's own background goroutines follows the same split — running out of budget there leaves the store open but still settles, since the server is already down and no client is waiting on those goroutines; reporting otherwise would exit non-zero for a shutdown healthier than the `StopForced` one that exits zero (issue #75)
- `lifecycle.go` — `StopServer` bounds `grpc.Server` shutdown with a tri-state outcome (`StopGraceful`/`StopForced`/`StopHung`). Both `GracefulStop()` and `Stop()` block until every connection is gone, so each runs in its own goroutine — calling either synchronously would itself consume the budget `StopServer` exists to enforce. `shutdownGrace` (3s) sits below grpc-go's own hardcoded 5-second timer between a graceful shutdown's two GOAWAY frames, so a dead peer is forced down before the hub pays for grpc's own wait instead of racing it. `grpc.WaitForHandlers(true)` is deliberately not used — it turns the wait unbounded, which is the exact failure this file exists to bound (issue #75)
- `serveropts.go` — `ServerOptions` is the single source of the gRPC server options (credentials, identity interceptors, keepalive). Both `Hub.Start` and `hubtest` build from it, so tests exercise the production transport. The keepalive **enforcement policy** is load-bearing: grpc-go's default answers a client pinging more often than once per 5 minutes with `GOAWAY too_many_pings`, which would turn the agent's keepalive into a disconnect loop. This is also why **the hub is upgraded first**: an agent from v0.1.3 onwards against an older hub is disconnected on a ~30s cycle (issue #72). The interceptors are registered with `ChainUnaryInterceptor`/`ChainStreamInterceptor`, not `UnaryInterceptor`/`StreamInterceptor` — the latter panic when set a second time, so a second interceptor could not be appended. Chain order is execution order, and the drain guard runs ahead of auth: a hub on its way out has no interest in who is knocking (issue #75)
- `server.go` — gRPC service implementation
- `registry.go` — In-memory device state, event fanout to subscribers; a heartbeat from a device the hub had demoted flips it back to `online` (fresh caller IP, stored SSH port + shares) and broadcasts `DeviceOnline`, so peers remount without waiting for a full session re-establishment. Recovery is gated by `canRecover`/`recoverAndAnnounce`: only a device whose event subscription is still open qualifies, and the guard is evaluated under the subscriber lock together with the write AND the announcement (a broadcast published outside that section would leave peers with `DeviceOffline` then `DeviceOnline` for a departed daemon) — `Deregister`/`Leave` close the subscription first and `Drain` (hub shutdown) takes the write lock, so a late in-flight heartbeat can never resurrect a daemon that deliberately went away (issue #69). `CloseAllSubscribers` is the measured fix for #75: a healthy agent's Subscribe stream kept `GracefulStop` waiting the full 29.99s (3 failed heartbeats on the agent's own 10s cycle) before SIGKILL, against 11ms for an agent that had already deregistered — closing the subscription is the only thing that differed. It takes the WRITE lock because `Broadcast`/`BroadcastAll` send under the READ lock; closing a channel under a read lock races a concurrent send — the sweep's own final `DeviceOffline` — and panics with "send on closed channel" on the very path being fixed. Callers must broadcast BEFORE calling it: a receive from a closed buffered channel drains the buffer first and only then reports `!ok`, so events already queued still reach their subscriber (issue #75)
- `heartbeat.go` — Monitors device liveness (30s timeout by default, stale-check every timeout/3; `--heartbeat-timeout` flag or `heartbeat-timeout` config key). The demotion re-applies its staleness condition at write time (`MarkOfflineIfStale`), so a heartbeat arriving between the sweep's SELECT and its UPDATE keeps the device online and no false `DeviceOffline` reaches peers (issue #69)
- `pairing.go` — Invite code generation, validation (5-min TTL, 5-attempt limit)
- `store/` — `Store` interface (`store.go`) with SQLite implementation (`sqlite.go`). Schema: devices, shares, pairings, pending_invites. Row-addressing writes report a missing device as `store.ErrNotFound` instead of succeeding silently (an UPDATE matching no row is not an SQL error), and status changes go through the conditional `MarkOfflineIfStale`/`MarkOnlineIfOffline`, which report whether the row actually changed so exactly one writer broadcasts the transition (issue #69). `MarkAllOffline` marks every online device offline in ONE statement; it backs both ends of the hub's life — the bounded shutdown sweep and the startup reconciliation. The single statement matters because the store is opened with `SetMaxOpenConns(1)` and `busy_timeout=5000`: a per-device loop would make shutdown cost proportional to device count against a connection that can individually wait five seconds behind a concurrent `hubfuse-hub issue-join`, easily outlasting the SIGTERM window on its own (issue #75)

### Agent internals (`internal/agent/`)

- `daemon.go` — Orchestrator; supervises the hub session — on event-stream death it re-runs Register→Subscribe with backoff so roaming/IP changes recover without a daemon restart (issue #61); a background mount-health monitor (`runMountMonitor`/`reconcileMounts`, 15s default, `HUBFUSE_MOUNT_MONITOR_INTERVAL` override) periodically reconciles desired mount state — it triggers Mount's generation-bound single-flight probe for each mount, which is a no-op for healthy/unknown mounts and tears down-and-remounts confirmed-dead ones (ENOTCONN or missing path, issue #67); the sweep re-reads config and online peers before *each* `Mount` (`currentDesiredMount`) so a mid-sweep config reload or `DeviceOffline` cannot be undone by a stale snapshot, and repeated *establish* failures back off exponentially per mount (10m cap) while probes of existing entries always run, so healing is never gated (issue #67); `processInitialDevices` prunes vanished peers from `onlineDevices` on re-register (issue #67); each session runs on its own cancellable context (`newSessionCtx`), which is what lets `noteHeartbeatFailure` end a session the daemon has decided is dead — cancelling it makes `Recv` fail, the one signal `supervise` acts on; `Register` is bounded (`registerTimeout`) so a reconnect attempt cannot be swallowed by a dead-but-unclosed connection (issue #72); liveness never queues behind mount work — `sessionOnce` starts the heartbeat loop (`startHeartbeat`, sync.Once) the moment the hub ACCEPTS the registration and before `processInitialDevices`, whose synchronous mounts can burn the full mount-verify window per stale entry; `runServices` only re-asks as an idempotent safety net (issue #69); the hub connection now lives under `sessionMu` alongside `sessionCancel` and `heartbeatFails` — one mutex, because two would give the heartbeat path and the reconnect path opposite lock orders (ABBA) — and every reader resolves it through `hub()` at call time; no RPC and no `hub()` call ever happens while `sessionMu` is held; `Shutdown` claims the connection once (`takeHubClientForShutdown`) and uses that single snapshot for BOTH Deregister and Close, because reading the field twice would let a replacement land in between and fail the in-flight Deregister with `ErrClientConnClosing`, which aggregates and makes `hubfuse stop` exit non-zero on a healthy stop (the #69 contract); `reconnectSession` replaces the connection when, and only when, a session attempt expired against the daemon's OWN deadline (`errSessionTimedOut`, decided by `ourBudgetExpired`) — never by looking at the gRPC status code, because a hub can answer `DeadlineExceeded` itself on a completed round-trip, and in the draining-after-GOAWAY path documented in grpc-go's source every attempt's code is `Unavailable` while the call dies on the caller's deadline, so a code-based classifier would miss the very case the replacement exists for; the predicate is read from the per-call context BEFORE it is cancelled, since `cancelReg` runs before the error is inspected and afterwards the context is always in error; exactly ONE replacement happens per episode (a local var in the loop, restored by a successful session) — measured: a kept channel misclassifies once and then self-corrects at 0ms per attempt, while a replaced one returns to IDLE and pays the full connect budget again on every retry, so swapping every round would turn an ordinary wifi drop into a 20s-per-round stall; the swap is a compare-and-swap against the client the failed attempt actually used; the heartbeat failure counter is NOT reset after a replacement — `newSessionCtx` clears it when the next session comes up, and clearing it early would only delay the heartbeat detector, the one thing that saves the daemon if the replacement wedges too; `subscribeWithBudget` bounds the ESTABLISHMENT of the event stream (a timer cancelling a child of the session context, disarmed once the stream exists) while the stream itself still lives on the session context, because unbounded a session attempt could park in `NewStream` forever with no error, no backoff and no log line — `seedNicknamesFromHub`'s `ListDevices` and the config-reload `UpdateShares` (which used to run on `context.Background()`) are bounded too (issue #77)
- `client.go` — gRPC client wrapper. Every hub connection is dialled through `dialOptions`, which sets gRPC keepalive (`PermitWithoutStream`, detection within ~15s — a third of the hub's liveness timeout): without it a connection that dies half-open is indistinguishable from an idle one, the event stream never ends, and the device stays offline forever with its shares unmounted on every peer (issue #72). Every unary response carrying `Success` is validated, so an application-level refusal (`Success=false` with a nil gRPC error) becomes a Go error wrapping `ErrHubRejected` rather than a silent success — a pruned identity now fails to start instead of logging `registered with hub` and writing a PID file (issue #69); `dialOptions` also sets `grpc.WithDisableServiceConfig()` — load-bearing, not a tuning knob: the default scheme is `dns` and grpc-go's resolver reads a `grpc_config` TXT record by default, so whoever answers DNS on the LAN could otherwise hand the client `waitForReady` and turn "the hub is unreachable" from an immediate failure into a call that blocks to its deadline, disarming the classifier from outside (issue #77)
- `heartbeat.go` — Heartbeat loop (10s default, `HUBFUSE_HEARTBEAT_INTERVAL` override). `maxHeartbeatFailures` consecutive failures end the hub session (`noteHeartbeatFailure` cancels its context) — keepalive covers a transport nobody answers, but a hub that answers HTTP/2 PINGs while its RPCs go nowhere only a real call can detect, and the heartbeat is the one that runs on a fixed cadence (issue #72). Unlike the mount-monitor knob, a non-positive value never disables it: a daemon that stops beating is guaranteed to be demoted and unmounted by every peer. Every call carries its own deadline (the interval, floored at 2s) so one hung RPC on a half-open connection cannot silently stall liveness (issue #69)
- `connector.go` — `Dial` produces one connection and returns — no retry loop, because its caller is already inside `reconnectSession`'s backoff and nesting two would make the outer timing a fiction; `Connect` keeps the backoff loop and delegates to `Dial`. TLS credentials are loaded once and cached, lazily, caching only success: re-reading them per dial is a torn read of three files `hubfuse join` writes with three separate `os.WriteFile` calls, and a repeat join can mint a different `device_id` — changing the CN, which IS the daemon's identity to the hub; the accepted consequence is that certificate rotation now needs a daemon restart (issue #77)
- `mounter.go` — SSHFS mount/unmount lifecycle; mount tool is selectable via the `mount-tool` config key (see the `mountBackends` table); `Mount` remounts a peer when its IP/port changes and `buildMountArgs` adds sshfs `reconnect`/`ServerAlive*` keepalive opts so a same-IP TCP blip self-heals (issue #61); `Mount`'s same-endpoint branch uses a generation-bound single-flight probe with tri-state health classification (healthy/dead/unknown) and tears down/remounts only confirmed-dead mounts (ENOTCONN zombie, issue #67); the daemon's desired-state reconciliation loop calls `Mount` for each desired entry, driving probes through the single-flight registry
- `sshserver.go` — Embedded SSH server (default port 2222) for incoming SSHFS
- `config/` — KDL format config parser (`config.go`), diff detection (`diff.go`), hot-reload via fsnotify (`watcher.go`)

### Shared utilities (`internal/common/`)

TLS cert helpers, structured logging setup, protocol version constant, common error types.

## Key Patterns

- **Config format**: KDL (parsed via `github.com/sblinch/kdl-go`), not YAML/JSON
- **CLI framework**: Cobra (`github.com/spf13/cobra`)
- **Data layer**: All hub persistence goes through the `store.Store` interface — add new queries there, implement in `sqlite.go`
- **Events**: Registry fans out events to subscriber channels; agents process them in `events.go`
- **Integration tests** (`tests/integration/`): Spin up an in-process hub with in-memory SQLite, create TLS certs programmatically, and test full gRPC flows
- **Scenario tests** (`tests/scenarios/`): End-to-end hub + daemons using a stub sshfs (`tests/tools/stub-sshfs`, selected via `HUBFUSE_STUB_MOUNT_DIR`); the stub harness is faithful — a mount is alive iff its JSON marker exists and its PID is running (`internal/agent/stubmount.go`), so killing the stub simulates a dead sshfs (issue #67). Timing is shortened through explicit handles rather than sleeps: `helpers.StartHub(t, helpers.WithHeartbeatTimeout(...)/WithRetention(...))` on the hub side, `HUBFUSE_HEARTBEAT_INTERVAL`/`HUBFUSE_MOUNT_MONITOR_INTERVAL` on the agent side. A connection that dies without either side being told is expressed with `tests/testrelay` — a forwarder that silences existing connections without closing a socket (issue #72). A connection that stays healthy at the transport level but not the application one — HTTP/2 PINGs still answered, the event stream keeps its socket, only the calls go nowhere — is expressed with `tests/testwedge` (`Wedge()`/`WedgeAll()`/`WedgeFast()`), which a TCP forwarder like `testrelay` physically cannot express, since inside TLS a PING frame and a request frame are indistinguishable; it is deliberately connection-scoped, which proves only that IF a wedge is connection-scoped a fresh connection is the way out, not that production wedges are of that kind (issue #77). A mount that must never succeed is expressed as a default-deny share — the SFTP handler denies the listing, the stub exits before writing its marker, and the mounter genuinely waits out its verify window (issue #69). `helpers.Hub.Stop`'s cleanup wait is derived from `hub.DefaultShutdownBudget` (plus a margin), never a second hardcoded literal, so it can never silently sit below the budget it polices; a hub's exit is observed via `cmd.Wait()`, never `syscall.Kill(pid, 0)` — signal-0 against an unreaped zombie still returns nil and would report an exited process as alive (issue #75)
- **Release versioning**: Lives in the `internal/version` package (the single source of truth for both binaries); GoReleaser injects version metadata via ldflags into that package's vars (`-X github.com/ykhdr/hubfuse/internal/version.{version,commit,date}`), NOT into `main.*` — wire any new version strings there
